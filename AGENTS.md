## The project in five lines

- **IMR Reef ID** is a static web app (plain HTML/CSS/JS, no build step, GitHub Pages) live at <https://ppericard.github.io/coral-id-imr/>. Named IMR Coral ID until 2026-11-03 (Pierre: corals now, fish and benthos next); the address and the repository name change later (ROADMAP). <!-- rename-app: keep -->
- It teaches the **39 coral genera on the IMR slate** (Institute for Marine Research, Dauin, Philippines): 34 numbered genera that IMR surveys track, plus 5 starred look-alikes (Duncanopsammia, Alveopora, Merulina, Cyphastrea, Halomitra) that are not tracked but must be told apart; and, since 2026-11-02, **Millepora** (fire coral: not a hard coral, so not on the IMR coral list, but on the IMR benthic slate and very common at Dauin and in ReefCloud photos), which counts like them: 40 genera in the games and the progress (`slateGenera()` in `app.js`).
- Owner: **Pierre Pericard** (GitHub `ppericard`), Research Fellow at IMR since October 2026. Users: Pierre and the Research Assistants (RAs) he trains, most of them on phones.
- RAs' first job is genus-level labelling of top-down benthic photos in **ReefCloud**, so growth form alone is never enough: the app must teach genus recognition.
- Path in the app = **Learn → Practice → Identify** (the order RAs work in), plus **My progress** and a Pierre-only **admin** back-office (`admin.html`).

## Working mode: the integrator and the merge contract (Pierre, 2026-11-05)

**The only place that says who merges and when.** Every other mention points here; change it here only.

- **One integrator.** The main agent of a Claude Code session is the integrator: it starts as many subagents as useful, each on its own branch, worktree and PR (How to make a change 16), checks their work and merges it. Subagents build, test, run the review loop (How to make a change 17) and report to the integrator; **subagents never merge**.
- **Few heavy subagents at once**: about 3 that build or run tests (more overloaded the cloud machine and crashed it); light ones (reading, reviewing, searching) do not count.
- **The merge contract.** The integrator merges a PR on its own, at any hour, only when all of these hold:
  1. every check is green on the current head, and no failed job was re-run to get green (How to make a change 17);
  2. every Codex finding is fixed or answered, every review thread resolved;
  3. **every choice in it was already decided with Pierre**: a standing rule, a ROADMAP row he agreed with its spec, his words (quoted with their date in the PR's "Decisions" section), or a decided process (once he agreed how a thing is done and checked the first results, its outputs ship without asking him item by item: fish photo judging on the agreed rubric, per-species photo pre-proposals; only a change to the process itself waits for him); the PR's "Choices I made" section is empty;
  4. it was rebased on `origin/main` right before the merge (Publish commits land without PRs) and goes in as a squash merge titled `… (#N)` (How to make a change 6).
- **The integrator decides the small choices; Pierre decides the ones that matter** (Pierre, 2026-11-05: "I don't want to validate micro-details; I want to validate every choice that has an impact"). A choice **with impact** goes to Pierre: something players see or feel differently (a new screen, a game rule, a learning value, content, a photo choice), anything costly to undo, or a choice that commits later work (a data format, a structure, a convention other code will follow). A choice **without impact** is the integrator's own and ships under the contract, listed in the PR's Decisions section as "integrator's call": a clearer word in a text, a frame moved a few pixels because it overflowed, the fix of something plainly broken, a name inside the code, a test. When in doubt, ask.
- **Otherwise the PR waits for Pierre.** A choice with impact that he has not made (a design option, a wording players read, a layout, a default, a threshold, a changed game rule) is brought to him as a question (below); the integrator merges once he has answered, his answer pasted into the PR. **A choice is never merged on silence** (Pierre, 2026-11-05): once something is presented to him as a choice with a recommendation, it waits for his answer, even when it looks reversible and invisible to players (side effects show up later, above all in how the game behaves); there is no "default unless he objects". **This does not make game changes wait**: a PR that holds only decided things merges under the contract, whatever it touches, game included. After a merge that changes what players meet or how the game behaves, tell Pierre in one line what went live, so he can check it in the game (information, not a question).
- **Always ask first**, even when it looks decided: anything destructive or irreversible (history rewrite, deleting data, bulk changes to his curation, the sheet's column layout), anything about money, accounts or access, anything sent outside the project.
- **One writer for [`docs/STATUS.md`](docs/STATUS.md)**: the integrator writes it (overwritten at each stop, never appended); subagents never edit it and put their questions and state in their report to the integrator.
- **Questions to Pierre**: in batches rather than one by one (unless one blocks work), in French in the chat, numbered for good (Q1, Q2…, never reset): the last number used is in [`docs/STATUS.md`](docs/STATUS.md), so the numbering carries across sessions and Claude accounts; open questions wait in STATUS "Questions for Pierre" until he answers (his answer then goes into the PR). Each gives one or two lines of context (he does not remember everything as an agent does; he may ask for more), the question, screenshots **sent as files in the chat** when it is visual, and the integrator's recommendation, so he can answer in a word ("Q1 oui, Q2 B"). When and whether to ask: Rule 0 and its quiet hours.
- **Data access** (Pierre, 2026-11-05): any agent, subagents included, may **read** the sync sheet ("IMR Coral ID – RA progress", its id in HANDOVER "Code.gs") through the Google Sheets / Drive connector, read-only, real names included: no anonymisation between agents. **Writing** to the sheet is the integrator's only (never a subagent), and only with Pierre's explicit one-off permission for that one correction. A subagent without the connector gets what it needs downloaded by the integrator, analyses it, and the integrator puts the real names back against the results for Pierre (he knows the players and matches results to people). Names never go into anything committed or published (rule 20f). Real-data checks (rule 14g, tier 3) may be run by any agent; their data and named results are never committed. <!-- rename-app: keep -->
- **Reports and events, at every session start and every morning** (Pierre, 2026-11-05): the integrator reads the players' reports (sheet tab "Reports") and the app's events and errors (tab "Events": `err`, sync "save failed", old app versions) since the last check, and gives Pierre a short summary with real names, leaving out what he already handled or excluded (curation exclusions, reports marked done in the admin). The time of the last check is in [`docs/STATUS.md`](docs/STATUS.md) ("Last checked: reports and events"); `tools/brief.py` cannot read the sheet (the connector is the agent's), so it only reminds of this step. Rule 0 decides when the summary reaches him (not in quiet hours).
- **The `needs-pierre` label** marks a PR that waits for Pierre. It is the integrator's own reminder (Pierre does not browse GitHub), not the source of truth: before merging, read the PR's open questions themselves; remove the label in the same step that records his answer, so a stale label never blocks a merge and never hides a question.
- **If Pierre switches back to claude.ai Projects** (a coordinator chat with no repository access, each thread its own Claude Code session): each thread is its own integrator and merges its own PRs under this same contract.

## Rule 0: Pierre's working hours (every agent, every session, phone included)

Pierre set this rule himself (2026-11-04) to keep AI-assisted development sustainable for months and years: it protects his sleep, his health and his evenings. It comes before every other rule. Times are **Manila time (Asia/Manila, UTC+8)**, every day.

**It limits Pierre's time, not the agents'** (Pierre, 2026-11-04: "the goal is not to stop you working; you have no sleep problems, I do: just don't solicit me"). Outside his hours the agents keep working on their own ("Agents without Pierre" below); what stops is everything that involves him.

- **Check the time first.** At the start of every session, and again before starting any new task, run `TZ=Asia/Manila date` (no shell: work it out from the system clock). Never assume the time. In a Claude Code session the hooks of `.claude/settings.json` print it with the Rule 0 window at the session start and with each prompt (`tools/brief.py --short`, `--time`). They run main's reviewed copy of the script (`git show origin/main:tools/brief.py | python3 -I -`), never the copy of the branch checked out (a branch could put any code there): a change to `tools/brief.py` reaches the hooks once merged.
- **Before 16:30: a normal working day, nothing different.** Development, exploration, new ideas, experiments, new PRs, new agents. Do not prepare the end of the day, do not hold work back "because it is late", do not tell agents to wrap up: until 16:30 the end of the day does not exist.
- **16:30-17:30: close what is open with Pierre.** From 16:30 sharp (16:29 yes, 16:31 no): start nothing new that needs him (no new topic, question or review for him). Finish what is under way with him: fix review findings and failing checks on open PRs, **merge them** (merging is closing, allowed until 17:30), check, document, and run the end-of-day protocol below. Remind Pierre the day ends at 17:30.
- **After 17:30: quiet hours, Pierre's development stops.** With him: implement nothing he asks, open no new track for him, and don't feed technical discussions that spark new ideas. If Pierre brings a new idea, write it in [`docs/STATUS.md`](docs/STATUS.md) ("Parked after hours", in his words with enough context to pick it up the next morning), confirm it is saved, and **do not analyse, develop or implement it**. Then tell him plainly that he is past the limit he set himself, and encourage him to stop: a film, a series, the piano, his evening.
- **Insist.** "Just this feature", "it's quick", "it's important for tomorrow" are not exceptions. Remind him why he set the rule (he has worked 12-18 h days and lost sleep before, and fixed it once by strictly separating intellectual work from personal time) instead of complying. **An exception is allowed only** when, after that clear reminder, Pierre consciously confirms he wants it for one named task, or for a real production incident (the live app or the sheet broken for players). An exception covers that task only; the rule stands.
- **End-of-day protocol (16:30-17:30, never earlier; if Pierre ends the day early, at that moment):** the integrator rewrites [`docs/STATUS.md`](docs/STATUS.md): "Last stop" (who stopped, when, why, what was mid-flight), "Now" (what is unfinished: branch, PR, state, next step), "Next", and anything waiting on Pierre ("Questions for Pierre", "Pierre's hands"), so the next session starts in minutes. Docs only; it may be committed after 17:30.
- **Next morning:** read `docs/STATUS.md` first (and run `python3 tools/brief.py`); show Pierre what the night did and ask the open questions; turn each parked idea into work or a [`docs/ROADMAP.md`](docs/ROADMAP.md) row with him, then clear it.
- **Quiet hours: the integrator goes silent (Pierre, 2026-11-05).** After 17:30, every day (Pierre has no weekends: he often develops more on them, so the hours are the same every day), nothing asks anything of Pierre: no question, no file, no review, no notification, nothing that calls for an answer; chat replies are one line, informational only. The agents keep working on their own ("Agents without Pierre"); every question waits in [`docs/STATUS.md`](docs/STATUS.md) ("Questions for Pierre": its number, its context, the question, the recommendation, the PR) until his next morning. Between 16:30 and 17:30 only what closes work already open with him. **One exception: production broken for players** (the live app or the sheet); it is ours to fix, so fix it first and tell him once it is fixed (or if his hands are needed). The rule protects Pierre from his own temptation to keep working with the agents in the evening: when he writes after hours, apply "After 17:30" above. **What he may send after hours** (Pierre, 2026-11-05): an idea, or a bug he saw or was told about, dictated to get it out of his head: save it (an idea in STATUS "Parked after hours", untouched until the morning; a bug may be worked on at once by the agents, on their own, without involving him), confirm in one line, and encourage him to stop. If he sees a big problem and insists on working on it with the agents now, even in the middle of the night, that is his conscious exception ("Insist" above): remind him once, then work with him; otherwise insist strongly that he stops, and keep every notification silent or at the very least.
- **Agents without Pierre (evenings and nights).** Keep working on your own, as far as possible, on work Pierre already agreed (ROADMAP "Next", STATUS "Now" and "Next", open PRs), up to a blocking point or a decision that is his or cannot be undone. **Never solicit him** (quiet hours, above). Park every question in [`docs/STATUS.md`](docs/STATUS.md) "Questions for Pierre" (a subagent puts it in its report; the integrator writes it there) and move on to other work.
  - **Merging: the merge contract, exactly as by day** ("Working mode" above; night changes when Pierre is asked, not what may merge: a sheet-script change that belongs to a decided track ships at night as by day). What waits for Pierre stays on its branch, not in production, with its screenshots (sent to him in the morning) and a one-line summary in STATUS "Now": anything players see that he has not approved (new screens, wording, design, a changed game rule), editorial or curation choices (photos, names, content, rule 27c), anything to do with money, accounts or access.
  - Every other rule applies exactly as by day. Same machine limits as by day (about 3 heavy agents at once, one smoke at a time). Before 08:00 Manila, the integrator writes the morning report into STATUS "Last stop" and "Now": what merged, what waits for his eye, the questions ("Questions for Pierre").

## Standing rules from Pierre (do not break these)

These came from Pierre's explicit feedback. When in doubt, follow them over your own taste, and ask him rather than guessing.

### Content and sources
1. **Never contradict or "correct" the IMR course or its lecturers** in the app. Keep the IMR wording (families, lecture lines, mnemonics, spellings). Where another source differs, add at most a discreet, dated, sourced note ("Source X (year) says…", shown as "Other sources" from `gen[g].info`), never "the lecture is wrong/outdated". Obvious slide slips are silently not reproduced and mentioned to Pierre only. When a source is old, trust IMR unless a very reliable *recent* source says otherwise; IMR trainers may be more up to date than the literature. Why: Pierre is new at IMR and the app is used there; visibly correcting the trainers would hurt his relationships ("Je ne veux pas me faire des ennemis").
2. **Never invent categories or information.** Groupings come only from existing references: IMR Lecture 6 groups (1-11), Coral Finder 2022 categories/boxes, the 7 IMR growth forms, or a mix. Every clue, label or pair carries its source (slide number, CF page/box). Claude-made look-alike "families" were rejected.
3. **IMR lecture cues are the most important content.** Two levels: the **ID tip** (`gen[g].qt`, from `tools/id_tips.txt`) is SHORT, 2-3 essentials, shown everywhere (quiz feedback, cards, ID tips view, comparisons) in a highlighted box; the full lecture cues (`gen[g].imr`, incl. review slides and presenter notes) appear only on the genus sheet under "IMR lecture notes".
4. **Growth form is an entry point only**, never genus-specific and never a strict filter (rank, don't filter). Photos use the 7 IMR (AIMS lifeform) forms: Branching, Tabulate, Encrusting, Foliose/Plating, Massive, Submassive, Mushroom (+ "x" too close to tell, + separate "polyps extended" flag). One form per photo, the dominant visible one. Never group or pick genera by growth form either (Pierre, 2026-11-03, on the custom quiz's selection screen: many genera take 3-4 forms or more, only the solitary mushroom corals keep one): a list of genera is A-Z, the slate order or the IMR lecture groups. The polyps flag ✿ only for polyps visibly extended at colony scale, only for the Coral Finder "extended by day" genera (Alveopora, Duncanopsammia, Goniopora, Heliofungia, Plerogyra, Tubastraea), never on macro photos.
5. **Everything produced is in English** (UI, docs, data, commit messages, artifact titles). Pierre chats in French; only chat may be French.
6. Open discrepancies between sources (questions for an IMR trainer, nomenclature points, content questions) are listed in `points.json`, which Pierre settles in the admin (Inbox › To do › Points; Pierre, 2026-11-05: he never reads a text list), in neutral wording (rule 1). Don't settle them yourself. The slide text is not the whole course: some points are only said in class or only shown in an uncaptioned photo, so a criterion missing from the slides is "check with an IMR trainer", never "not taught".
6a. **Fish names and presence** (Pierre, 2026-11-03): the name shown and expected is the EventMeasure / IMR reference PDF name (EventMeasure's fixed pick list may lag WoRMS); the WoRMS accepted name is an indication beside it, and both are accepted when typed. A likely slip in the PDF is kept and flagged for Pierre, never corrected. Pierre's own iNaturalist observations (`ppericard`), two halves (Pierre, 2026-11-04): **photos**: his photos identified to the species stay usable as photos of that species even when Needs ID (his only: he names a species only when nearly sure, otherwise he stops at the genus or the family); **presence**: they no longer confirm that a species is present on their own, in the Philippines or near Dauin (rule 6g: he is one observer like anyone, Research Grade only); a species seen only as Needs ID near Dauin is "not confirmed near Dauin", never "never seen". ARCHITECTURE.md "Fish content".
6b. **Starred genera** (Duncanopsammia, Alveopora, Merulina, Cyphastrea, Halomitra) are on the slate *because* they look like surveyed genera: never show them as a separate "not covered" group; `shownGroup()` places them in the lecture group of their Coral Finder look-alikes (display only). On the one-at-a-time path a starred genus opens only after the surveyed genera its card compares it to have been met (Pierre, 2026-11-03: a beginner met *Duncanopsammia*, "Like *Turbinaria*…", before *Turbinaria*); the references come from the data (`core.js` `starRefs`), never a list in code; Open all still opens everything at once. Since 2026-11-04 every game follows that one path (rule 6d), so the rule holds in the Duel tab, Memory and the custom quiz too.
6c. **Fish groups come from the regional identification key, within the region the key covers** (Pierre, 2026-11-04: the book's index is "reference no. 1 in every dive centre", so nobody questions the groups). For the Indo-Pacific the key is the index of the 20 identification groups of the book *Reef Fish Identification – Tropical Pacific*, 2nd edition, which the IMR course follows: the app shows its group numbers and titles (not the 10 IMR shape groups), credited to the book. Its citation is written once, in the key (`cite` in full, on the families page; `short` everywhere else), never copied into code or docs: a change is one edit. **Every fish family added to any circle must attach to one of the key's groups**: `tools/build_fish.py` fails, naming the node, when a node in the game has no group or spans two without an explicit `keyGroup` (null with `keyWhy` only while a node waits for Pierre's decision; the build lists it). The keys are data (`tools/fish_source.json` `keys`, the one in force `deploy.key`): a deployment in another region uses that region's key, and a region with no key has no such rule; adding one needs no code change. ARCHITECTURE.md "Fish content".
6d. **One progression path for every game** (Pierre, 2026-11-04: "the quiz, the Duel tab, Memory and any future game or mode, no exceptions"): the photo quiz is the path that opens genera (one at a time, the ★ rule, Open all); every other game or mode draws only from the genera the player has unlocked, `model.js` `unlocked()`, the one source of truth, and never opens a genus (no card from a game). A new game uses `unlocked()` too; the Tools' games through `proto/lab.js` `labPlay()` (the reference tools keep every genus; wrong choices may name any genus, as the quiz's). docs/LEARNING.md "One progression path for every game".
6e. **ID cues and their doubts are for the place we learn** (Pierre, 2026-11-04: "the goal is to recognise corals here"): evidence and examples in ID content (notes, tips, look-alikes, the reasons a cue may fail) come only from species found around Dauin, at most in the Philippines. Never add doubt to a cue with a species from elsewhere (the Caribbean, the Red Sea…). **A species is present in the Philippines** by rule 6g (the one presence rule; Needs ID alone, Pierre's included, never confirms). Check it before citing a species, with observers and not only Research Grade counts (batched, rule 6f; `tools/presence.py` `species_presence` does it per genus), and say in the PR which test each species passes. Example: the Favites notes of 2026-11-04 (`tools/apply_favites.py` lists them).
6f. **iNaturalist API: respect its terms** (Pierre, 2026-11-04): about one request per second at most (sleep between calls; never parallel), batch many ids or taxa into one request instead of many small ones (`id=1,2,3`, `taxon_id=a,b`, `observations/species_counts` on a family rather than one call per species), and always send a User-Agent naming the app. Retry a 429 or a 5xx after a pause, never in a tight loop: `tools/fetch_local.py` paces and retries (PR #481); a new tool does the same. A review of every iNaturalist tool for batching is in ROADMAP.
6g. **Presence: one rule for every species, fish and corals** (Pierre, 2026-11-04: "the same scientific rigour for everyone, me included"). **Confirmed in the Philippines** = any of: (1) Research Grade iNaturalist observations in the country (place 6873) by **at least 3 distinct observers**; (2) **at least 1** Research Grade observation in the country **and** an independent checklist that lists the species for the Philippines (fish: FishBase country checklist, Table 1 "present"; corals: Corals of the World, a Philippine ecoregion; `tools/presence_checklists.json`): a checklist alone never brings in a species nobody observed; (3) **confirmed near Dauin**, which is Research Grade observations within 40 km of Dauin by at least 2 distinct observers, or the IMR reference list (fish: the EventMeasure PDF). Pierre (`ppericard`) is one observer like anyone else: his Research Grade observations count, his Needs ID ones confirm nothing, here or near Dauin (his species-level photos stay usable, rule 6a). Defined once in `tools/presence.py` and used everywhere presence is decided: `tools/build_fish.py` (`fish.json` `present`: in the game or out), `tools/fetch_fish.py` and `tools/fetch_local.py` (photos from abroad only of confirmed species), `tools/coral_presence.py` (`presence.json`: a coral photo taken abroad of a species not confirmed is flagged "out of rule" in the admin, never removed automatically: Pierre decides). Change the rule there, not in a tool.

### Photos
7. **Photo priority in every context: IMR lecture photos first, then Pierre's own (iNat user `ppericard`), then other iNaturalist observers and Coral Finder book photos only to fill gaps.** **Corals only, with a caveat** (Pierre, 2026-11-04): IMR lecture photos stay preferred for corals (few alternatives), but their provenance is uncertain: many are not IMR's own (from iNaturalist or the web without a proper source); trace them and credit or replace where the rights are unclear (ROADMAP). **Fish never use IMR slide photos** (most are not IMR's own, likely from ID books; photos with known rights abound); diagrams and figures are our own drawings. Covers and the first 3 ("featured") photos per view: IMR before Pierre's. IMR photos are never auto-rated Poor and never auto-excluded. Exception: the Coral ID Key mixes sources on purpose for variety. **Licences and trusted identifications for candidates** (Pierre, 2026-11-05, corals aligned with the fish): CC0, CC BY or CC BY-NC only, never share-alike (nor ND); the share-alike coral photos already on the site are his to keep or remove (admin To do › Share-alike), never removed automatically. In the Philippines tiers an observation identified by iNaturalist user `thamnasteroid` (by far the top identifier of stony corals there) at the genus or below is accepted, like a genus-level community ID, when no other current identification disagrees (a coarser one on the same line, e.g. the observer's "Stony corals", does not); abroad stays Research Grade and the presence rule (`tools/fetch_local.py` `LIC`, `EXPERTS`; ARCHITECTURE.md "Share-alike coral photos").

Only step-by-step Undo of his own actions; **no bulk reset/wipe button of any kind** (he refused it twice). The admin's Publish never writes a whole copy: it re-reads the published file and merges the draft onto it key by key (`merge3()`, PR #240, after a whole-copy publish from a stale tab lost curation on 2026-11-01). Keep it that way if you touch `save()` in `admin.js`. The **auto-sort** (Pierre, 2026-11-03) is the one thing that writes choices for him, and only through that same path: at each admin load it puts the candidate pass's sure judgments into his draft, for photos he has not decided, never replacing a value he gave, each one logged as auto (`curation.json` `auto`) and undoable one by one; his Publish sends them. Never make it write `curation.json` any other way. The fish auto-sort (admin plan PR 4, `autosort.js` `fishRun`) takes the same path into `curation.json` `fish`; it never writes `fish.out`, Pierre's "Not this" (the iNaturalist experts got the species wrong: his click only, never an agent's), and never proposes again a photo he marked so (Pierre, 2026-11-04).
9. Three views per genus: **colony**, **close-up** (10-30 cm part of a colony; code name `medium`, labelled "Closer" before 2026-11-01) and **corallites** (macro). A genus may have 2 levels: colony + close-up (its macro photos, also labelled "Close-up", Pierre 2026-11-01), never duplicate a photo to fill a view. Cover = mid-distance view, never macro.

Kelley / BYOGUIDES, `gen[g].book`) are **never in games**; on a genus sheet they appear only when Pierre pins one, or to fill a gap after every field photo; the Coral ID Key adds up to 3 approved ones for variety. ### Learning logic
12. **Time between sessions never decays progress, mastery or ability** (no spaced-repetition days, no decay, no "refresh"). It is a practical tool, not a retention or daily-habit app (no streaks, lessons, Duolingo-style units). Someone should be able to master everything in a few hours. **The seconds taken to answer a question are another matter** (Pierre, 2026-11-04: the rule was about days between sessions, Duolingo-style, not about the few seconds an answer takes): they are evidence about that answer and may weigh how much it moves the ability (a right answer given fast proves more than one given slowly: `core.js` `rtWeight`, docs/LEARNING.md "Response time"); never a decay, and never a penalty for being slow on its own. **One exception, time to plan the comeback after a break** (Pierre, 2026-11-02: "the no-time rule was there because the goal is not to bring people back every day like Duolingo; the goal is to learn as fast as possible, in a few hours or days. But for the comeback, time must be taken into account"): the time since the last answers decides the questions after a break (a new visit after 30 minutes without an answer opens no genus in its first 10 answers; the FSRS forgetting curve plans a comeback on genera answered right; `model.js` "Comeback after a break", docs/LEARNING.md). Progress (`s.pg`), mastery (`s.mx`) and the Elo ability (`s.th`) never decay with time: only answers (and how fast a right one came) move them.
13. **A wrong answer counts against both genera**: the correct one and the one wrongly given.
14. Difficulty is adaptive and continuous: per-genus player ability vs photo difficulty on one Elo scale (Pelánek 2016), ~80% target success, guaranteed variety and new photos, more single-view questions as the level rises (details in ARCHITECTURE.md). No manual Easy/Medium/Hard selector. Every account counts everywhere, Pierre's included (Pierre, 2026-11-04: his account is a real player's; the admin has no filter on his own answers or "test" accounts; the leaderboard's "hidden" changes only the public leaderboard). Starred genera are always included in Practice. Never split practice by lecture group.
14a. **Millepora and the bonus genera** (Pierre, 2026-11-01, changed 2026-11-02): *Millepora* is a slate genus for everything in the games and the progress (`BENTHIC`), with a warning on its first card and its sheet that it is not a hard coral nor on the IMR coral list, but on the IMR benthic slate. The other genera off the slate that are common at Dauin (`BONUS`: Isopora, Leptoseris, Heliopora, Sandalolitha, Pleuractis) are **opt-in**: offered once by a card when the player has met every slate genus (Add them / Not now; never in the first 10 answers of a visit or during a comeback, rule 12), and ⚙ Bonus genera On / Off any time (`Q.bon`). Once on they open one at a time like slate genera (no threshold, no weight cap of their own). They never count in the progress, their ID tips are the Coral Finder's (labelled so), their game photos (Millepora's too) are Research Grade iNat (or Pierre's) only. Details: ARCHITECTURE.md "Bonus genera". **No genus-specific case in code** (Pierre, 2026-11-03): the game genera (slate + Millepora + bonus) and the Key-only ones (the other `data.json` `x` genera) are defined once, `core.js` `BENTHIC`, `BONUS`, `slateOf()`, `gameOf()` (Python: `tools/genera.py`); use them, never `n === 'Millepora'` or a `!DATA.gen[n].x` filter for "game genus". In the admin the game genera come first (Candidates, Game coverage); Key-only genera get no Corallites candidates and a cap of `CAP.sheet` (6) colonies per view.
14b. **All photos of one game question come from ONE observation (same colony)** (Pierre, 2026-11-01). Never top up a missing zoom level with another colony: a colony with one view becomes a single-view question.
14c. **Answer choices get harder gradually** (Pierre, 2026-11-01: "at the very start it must be simple", traps appear little by little). In the photo quiz the wrong choices for a genus start easy (genera sharing no IMR growth form with it), and its look-alikes come in one by one, and soon (one after the first right answer, all three after about 5: look-alikes are one of the ways genera are learned), as the player's Elo ability on that genus rises (`FORMAT`, `trapsFor()`, `distractors()` in `app.js`). Duels stay look-alike pairs by design. Official IMR / Coral Finder look-alikes only *seed* the confusions: real player answers then decide which genera get confused (Pierre, 2026-11-01; confusion scores), pooled over every player first, then each player's own mix-ups weigh in as their answers on the pair build up (personal path, `pairConf`; performance only, never time). A genus never answered starts from the player's global level (`playerStart`, `core.js`: an Elo over all their answers, shrunk while they are few), so a strong player gets traps and harder photos on a new genus from its first question; "Learned" is still earned genus by genus.
14d. **Achievements reward learning, never time** (Pierre, 2026-11-01): unlocked by learning milestones (quarters of the way to learned, genera learned, progress, runs of right answers, duels, corallites, hard photos, Elo), never by time spent or days played; spread out so the first come within a few dozen questions (`core.js` `ACH`; check a new one's timing with the real game before adding it).
14e. **Learned = the silent mastery exam** (Pierre, 2026-11-01): a genus fills up to 95% with its progress, a moving average of its answers (since 2026-11-02, Pierre: right answers against its look-alikes count most, each point harder to earn than the last; docs/LEARNING.md); learned (100%) takes 5 exam questions slipped unannounced into the photo quiz, several answers apart, each as hard as the game gets (one photo alone, never seen, look-alike traps), all right, at least 2 of them typed from memory (Pierre, 2026-11-03: typed questions come in progressively as the level on a genus rises, never as an on/off mode; `model.js` `TYPED`). Any miss on the genus, or giving it as the answer for another one, restarts it. No milestone that a player can pass by luck or in a few questions.
14f. **The simplest algorithm that works** (Pierre, 2026-11-02: "the simpler the algorithm, the better; with 50,000 parts and 50,000 variables it gets ever harder to calibrate"). Don't add a variable, a special case or a hard-coded ramp to patch a problem: first rethink the rule or recalibrate the existing settings (example: the opening of genera became a slope on `OPEN.K` instead of new duel/opening knobs, docs/LEARNING.md). **Checks come in four tiers** (Pierre, 2026-11-05): **tier 0, always**: the unit tests and the CI smokes. **Tier 1, systematic for any change to the learning algorithm's behaviour**: any change to the learning path is checked over several seeds (`tests/profiles.smoke.js` profiles), not one run, and its effect on what players really learn with `node tools/learnsim.js` (the four profiles × 5 seeds, before and after, the same seeds, about 2 min; docs/LEARNING.md "Learning-outcome simulation"), with a small standard table in the PR. Five is enough (Pierre, 2026-11-03: "4 or 5 players were plenty to get an idea", no p-values wanted). **Tier 2, fine calibration**, an option, hopefully rare (Pierre): when a value is being chosen, or when two versions differ by less than their spread on the measure that decides (tier 1 inside the noise): 20-30 seeds, extended profiles, sweeps. **Tier 3, real data**: rule 14g.
14g. **Check algorithm changes against the real players, not only the simulation (Pierre, 2026-11-03; tier 3 of rule 14f).** Any change to the learning algorithm (Elo, progress, draw, opening, difficulty, typed questions…) is checked twice before its PR: in `tools/learnsim.js` (5 seeds, the four profiles: no learning path may break) and on the real answer log (read-only replay of the sheet's Answers tab, or a saved extract kept outside the repo): the change must not move the app's estimates away from what players really do, and should bring them closer (next-answer log-loss and calibration, Expected against actual, overall and by level band and question format). Where a replay cannot judge a change (a different draw asks other questions), say what was measured instead. The PR shows both tables; LEARNING.md keeps them. The real log is read through the Google Sheets connector, by any agent ("Data access" in "Working mode"; Pierre, 2026-11-05: no GitHub Action needed), for every change to the estimates and, Pierre insists (2026-11-05), **routinely** while the app moves fast and players play every day: it caught many problems in these last days.
14h. **The first-launch question initialises variables, never a path** (Pierre, 2026-11-03). "How well do you know corals?" (new to corals / had the IMR coral course / know corals well) is a forced choice in the welcome tour (or a card before the quiz), asked once to existing players under 50 answers and inferred silently from 50 on. Each answer only sets values of the existing model (`core.js` `CHOICE`: the level `playerStart` shrinks towards, when the open-all offer can come, Coral basics offered first); the one dynamic algorithm then runs the same for everyone, and a one-time fallback card per answer and direction when the answers do not fit (checked at 40 and 60 answers only, the global level against the band the answer predicts: "lower" sensitive, at one-sided 80% or the opening hold alone, its card a gentle Coral basics offer that never labels the player and moves the start variables one band down silently, the answer kept; "higher" at 95% with 10 genera met, the first answers as a guard). The full replay applies the answer's prior (RVS v3). A new variable there needs its learnsim check per answer, right and wrong (docs/LEARNING.md "The first-launch question"). **Each subject asks its own** (Pierre, 2026-11-04: the fish welcome question "works exactly like the coral one"): its words in `core.js` `SUBJECTS` `start`, the same answers and engine, its own record (`startKey`); never a subject named in the code that asks it.
14i. **Compute once, not on every phone** (Pierre, 2026-11-02): what can be computed once (in the sync sheet's stats, or in `data.json` at build time) and served to the app is preferred over recomputing it on each phone or in each admin session.
15. Visual recognition and fast side-by-side comparison beat theory. The 5-question observation routine is only for the very first contact. In the field people recognise genera by overall look; on photos they use the Coral Finder book (in the app, the Coral ID Key, which follows it): growth form first, then a quick visual comparison of the candidates. Quiz feedback shows corallite traits and lecture cues, never growth form as the reason.
15b. Short-term goal: ID on ideal photos, or on dives with time to look closely. ReefCloud point drills, realistic/degraded images, RealityScan and Metashape material are medium term (ROADMAP "Parked").

## How to make a change

1. Branch from `main` (fetch first: `main` moves often, see below). Run locally: `python3 -m http.server 8000` and open <http://localhost:8000>. To see and try the admin without a token, open <http://localhost:8000/admin.html?demo>: every page works on made-up players, answers and reports (`admin-demo.js` answers the sync script and GitHub calls in memory; nothing is sent, Publish is kept in memory, its storage keys are prefixed `demo:`). Use it for screenshots and to test an admin change; when you change a sync reply or an admin call, keep `admin-demo.js` in step. There is no build step. Tests: `node --test tests/*.test.js` (Node only, no npm), plus the page smoke test `node tests/pages.smoke.js` the question draw test `node tests/draw.smoke.js` and the admin demo test `node tests/admin.smoke.js` (all need Playwright; CI installs it in a temporary folder, never add a package.json); add one when you change logic they cover. Pure logic shared by app and admin (curation merge, progress merge, photo Elo) lives in `core.js` so it can be tested. Every PR runs `.github/workflows/checks.yml` (JS syntax, tests, JSON, `data.json` layout, Python, versions, and each Playwright smoke test in its own parallel job `smoke (<name>)` (pages and admin in two halves each, `SMOKE_PART` / `SMOKE_W`), `fail-fast: false` so every failing smoke reports; a new push cancels the run still going on the PR).
2. **Formatting** (`.git-blame-ignore-revs` lists the reformatting commits; run `git config blame.ignoreRevsFile .git-blame-ignore-revs` once for local blame): JavaScript and CSS (app, admin, Lab, tests; not `tools/`, HTML or JSON) are formatted with Prettier 3.9.10 and `.prettierrc.json` (print width 140). Before pushing: `npx --yes prettier@3.9.10 --write "*.js" "*.css" "proto/*.js" "proto/*.css" "tests/*.js"` (no package.json); the PR check fails otherwise. Prettier 3.3.3 (an old version picked from memory) dropped array elements inside a template literal in `proto/anatomy.js`, found by an AST comparison (2026-11-01): after a formatter upgrade, compare the syntax trees before and after, and run it until the files stop changing.
2b. **Which tests to run: the fast tier before each push, the full tier on CI** (test-suite review, 2026-11-04, approved by Pierre). Several agent sessions share one machine, and running every smoke on every push loaded it until fixed timeouts failed. CI runs everything on each PR, each smoke on its own runner, and reports every failing one. Locally, run what your change can break, once:
   - **Fast tier, before each push** (about 1-2 min): `npx --yes prettier@3.9.10 --check` on the changed `.js`/`.css` files; `node --check` on the changed JS; `python3 tools/check_versions.py` (consistency only: never bump a number, rule 3); `python3 tools/datajson.py --check`; `python3 tools/sync_core.py --check`; `node --test tests/*.test.js`; then **the one smoke part your change touches** (below). Docs-only changes: no smoke.
   - **Full tier**: CI on the PR. Run every smoke locally only when CI is down. After a big interface change, the brand-new-player replay of step 5 stays a separate manual step.
   - **Which smoke part**: `admin*.js`, `admin.css`, `admin.html`, `autosort.js`, `analysis.js` → `SMOKE_W=1280 node tests/admin.smoke.js` (`SMOKE_W=390` for a layout change). The question draw (`model.js`, the draw in `quiz.js`, `core.js` `photoSet`/`distractors`/the path) → `node tests/draw.smoke.js`, and `node tests/profiles.smoke.js` when the learning path changes (rule 14f). Fish, `SUBJECTS`, `UNITS` → `node tests/fish.smoke.js`. `sw.js`, the loader in `index.html`, photo sizes and fallbacks, R2 → `node tests/net.smoke.js`. In `tests/pages.smoke.js`, `SMOKE_ONLY=<part>[,<part>]` runs some of its parts: `tips` (`tips.js`), `relief` (the Duel tab's relief card, `quiz.js` `reliefShow`), `start` (the first-launch question, its fallback cards, the open-all offer: `startSmoke`), `signin` (sign-in, the `sync.js` UI), `replay` (the sheet's replay adopted), `overlays` (cards, prompts, the one-tap question, the tour), `credits` (Home, credits, header fit), `basics` (Coral basics), `visit` (the pages-opened summary), `main` (routes, sheets, lightbox, history: anything else in `app.js`, `app.css`, `index.html`; with `SMOKE_W=390` for one width). `SMOKE_PART=main|rest` is the half CI runs on one runner. Default (no variable): everything. `PAGES_ONLY=` (the older name) still works.
   - **One Playwright run at a time per 2 cores on the machine**: every smoke and every Playwright tool (`tools/learnsim.js`, `tools/perf.js`, `tools/rtprep.js`, `tools/og/make_og.js`) takes a slot from `tests/slot.js` before it starts Chromium, waits while the machine's load is above its core count, and gives the slot back when it ends (a crashed holder's slot is taken back). A new Playwright script calls `await require('./slot.js')(name)` (from `tests/`) the same way. A smoke loads Playwright's `chromium` through `tests/calm.js`, which opens every context in reduced motion (no entrance animation to wait for) unless the context asks otherwise (a check about motion, the brand-new player). Never run two smokes at once from one session; `SMOKE_SLOTS=n` changes the cap, CI ignores it.
3. **Cache busting: never edit a version number** (Pierre, 2026-11-04: five open PRs carried the same `sw.js` V, so each merge forced the others to bump again). The deploy stamps them (`.github/workflows/pages.yml` runs `tools/stamp_versions.py` on its staged copy): every `?v=` becomes a hash of the file it names, `LAB_V` and the `sw.js` Lab list one hash of the Lab files, the `sw.js` cache name `V` a hash of everything its `SHELL` keeps, and the pages get the deploy's build number (`<meta name="build">`, `sync.js` `appVer` reports `<build>-<hash>`). So a PR **never edits `?v=N`, `LAB_V` or `sw.js` `V`**, even after changing a file, and a merge never conflicts on them. The numbers in the source are frozen; a **new** versioned reference takes any number (`?v=1`), the same at every place it appears (`index.html` or `admin.html`, `sw.js` `SHELL` when the app loads it, `app.js` for a fetch). `python3 tools/check_versions.py` checks only that consistency (one value per file everywhere, `SHELL` lists what `index.html` and `app.js` load, the Lab list matches `LAB.files` and `LAB_V`); it has no `--fix` and no `--base` any more. Locally the browser may keep an old copy of a file you changed (no service worker on http): reload with the cache disabled. The sheet's `VERSION` (`tools/sync/Code.gs`) is not stamped: bump it by hand as before.
4. Editing `data.json` by hand is normal (the original build script reads a scratchpad that no longer exists). **Write it only with `tools/datajson.py`** (candidates waiting live in `cand.json`, admin only: read both with `load_all()`, write with `dump_all()`, which keeps in `data.json` only the candidates `curation.json` names) (`from datajson import dump` then `dump(d, path)`, never `json.dump`): one top-level key per line and one genus per line in `gen`, `course`, `cand`, `x` and `x.gen`, compact within a line, so two edits to different genera merge cleanly. After a hand edit, `python3 tools/datajson.py` puts the file back in that layout; the PR check (`--check`) fails otherwise. Prefer a small, re-runnable `tools/apply_*.py` script that documents the change.

Open the browser console: no errors. **After a big change to the interface or the flow, replay the whole app as a brand-new player** (Pierre, 2026-11-02, after an RA found the tour and the first genus card on screen together: the tests pre-set "tour seen" or "cards seen", so no test met both; not needed for internal code or small fixes, Pierre the same day): an empty browser, phone and desktop, light and dark, from the first load through the tour, the first cards, a few dozen questions (Again, duels, the offer, achievements), My progress, the other games, Identify, Tools, help and settings; screenshots at each step, every overlay alone on screen and closable.
