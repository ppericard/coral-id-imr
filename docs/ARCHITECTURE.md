# Architecture

How the app is put together. Rules and workflow are in [`../AGENTS.md`](../AGENTS.md); deferred ideas in [`ROADMAP.md`](ROADMAP.md).

## Overview

```
data.json (genus data + photo lists) ──┐
forms.json / quality.json / picks.json ├─> app.js (applyCuration + applySlots from core.js, applyForms) ─> pages
curation.json (Pierre's choices) ──────┘                                    │
                                                                            └─> progress in localStorage ─> Apps Script ─> Google Sheet
admin.html ──(GitHub Contents API, Pierre's token)──> curation.json on main ──> GitHub Action fetches approved photos
```

- Static site served by GitHub Pages from `main` via `pages.yml` (Actions source; migration and recovery in [PAGES.md](PAGES.md)). No framework, no bundler, no npm.
- A service worker (`sw.js`) caches the app shell for offline use (versioned cache `V` = `reefid-shell-vN`, replaced on each deploy; see "Names, storage keys and caches") and photos as they are viewed, in a separate cache `imr-photos-v1` that deploys never delete (capped at 2,500 entries, only good replies kept). Photos from R2 (see "Photos") go through it too: asked in CORS mode whatever the page asked (an `<img>` asks no-cors, whose opaque reply cannot be checked and costs ~7 MB of quota each in Chrome; the bucket allows the site), looked up under both addresses (R2 and the site's `img/`, so photos cached before the switch stay offline); when R2 fails (asked twice, 800 ms apart, then for 60 s not at all) the worker answers with the failure and the page picks the next source, the photo's online original or the site's copy (`photo()` in `sw.js`; it no longer serves the site's copy by itself, since the photos with an online original leave `img/`: "Photos"). `curation.json` is part of the shell, so the first offline launch after a deploy still has Pierre's choices; the app also keeps the last curation it read in `localStorage` (`reefid-curation-last`) as a fallback. **New versions reach players without a manual reload** (Pierre, 2026-11-02): each deploy changes `sw.js` (`V`), which the browser checks at each launch and the app re-checks when it comes back into view (5 min apart) and every 30 min (`swCheck`); the new worker installs in the background and takes over (`skipWaiting`, `clients.claim`), and the page then reloads itself when it next comes into view or at the next page change (`UPDATED`, `route()`), never in the middle of a page. A page from before 2026-11-03 has none of this (Pierre: RAs who opened one of the very first versions kept it open for days, so their answers never reached the sheet): on activate, the new worker asks each open app page (`index.html`) its version (`reefid-ver?` over a `MessageChannel`, answered by `app.js`); a page that does not answer within 3 s is reloaded by the worker (`client.navigate`) onto the new version, once. Every request to the sheet carries the app's version (`av`, sheet v25), and the sheet logs one without it in Events as kind `old` (with the name or anonymous id it carries), so such devices can be found. **A page left on a replaced version** (Pierre, 2026-11-05: the sheet logged "app before 2026-11-03: photo stats" on 11-03 16:57, 20:59 and 11-05 10:27, Manila, with no device): that message is what any `?stats=1` read without `av` gets (at most once an hour), whoever sends it: the row of 11-05 was the integrator's own `curl` of the stats, and those of 11-03 were most likely tools too (stats saved for `tools/learnsim.js --stats`), not players' devices; the admin page opened without a token (`admin.html?readonly`) read them without `av` too. Every read the repository makes now carries one that is no build number (`admin.js` `av=admin`, `tools/brief.py` `av=brief`, `tools/learnsim.js --stats live` `av=learnsim`; by hand `curl "<SYNC_URL>?stats=1&av=tool"`), checked by `tests/statsav.test.js`. Now: the app's photo stats request carries `av`, its anonymous device id `dev` (the Device of its events, which the Pages tab ties to the player's answers) and `up`, the minutes its page has been open (never from a local copy); the sheet (v50, `Code.gs` `behind_`) keeps the newest build reported (Script Property `BUILD_TOP`, a build far ahead of it refused) and logs in Events, kind `old`, Device the id, App the version, a device on an older build when its page stayed open 30 min (`OLD_OPEN`) on a version replaced an hour (`OLD_H`) before, or when it starts a version replaced a day (`OLD_STUCK`) before; at most once per device every 6 hours. A page that no service worker controls (a browser without one, such as a chat app's built-in browser) hears of no new version until it is reloaded: left as it is, since no player's device was seen in that case (ROADMAP). **Never in the middle of a question**: back in view, the page reloads only when no question waits for its answer (`QOPEN`, set by `quiz.js` `question`, cleared by the answer and by `route()`); Next in a game is a page change (`route()`), so the new version comes between two questions. The install copies a versioned file (`?v=`) or a font that a cache already holds instead of downloading it again (most deploys change a few files; it downloaded the whole shell, about 1 MB, which the takeover waits for), and asks the other shell files (page, `curation.json`, manifest, icon) with `cache: 'no-cache'`: from the browser's HTTP cache (GitHub Pages: 10 min) a new version could hold the page of the deploy before and run its old code (`sw.js` `get`, `fixed`; `tests/swcache.test.js`; the question guard `tests/update.test.js`). The admin page does the same (`admin.js`, every click is already in the draft; not while the draft could not be saved). Both listen for the takeover (`controllerchange`) from their first line: the admin used to add its listener at the end of `start()`, after `data.json` and `cand.json`, and a version that took over meanwhile (a new worker waits for the old one's fetches still in flight, then takes over once the old one is idle) went unseen, so that tab kept the old code. The takeover can come later (Chromium, 2026-11-03, from timestamps of both workers and Chromium's `content/browser/service_worker`): a busy old worker is stopped the moment it is idle, and a request that comes while it stops (the page's next file or photo) starts the old version again, which is then not asked to stop early: the new version waits until the old one has been idle 30 s, or at most 5 min after its `skipWaiting()` (Chromium's "lame duck" timer; with DevTools attached, as in Playwright, only that). It happens when a new version finishes installing while the page still loads (a launch right after a deploy, photos held ~1 s by the R2 retry): the player gets the new version later, never not at all. A page opened in the very instant of that swap can hang (Chromium, 2026-11-05, from Chromium's own worker states in `tests/net.smoke.js` check 9): its navigation goes to the old worker just started again, which Chromium stops a few milliseconds later with the request still in flight, and the page never loads until it is reloaded. Rare for a player (a deploy, a version waiting and a page opened within those milliseconds) and out of the app's reach (no page code runs yet); check 9 opens its pages only once no version is waiting. `tests/net.smoke.js` check 9 publishes each version while its page is quiet. Before, a slow line served the old cached page after 2 s, so it took one or two manual reloads. The install fetches each shell file on its own, up to 3 tries (with `addAll`, one failed request on an unstable line failed the whole install). Versioned files (`?v=` in the URL) and `fonts/` are cache-first (a new version is a new URL), so a launch needs no network once cached. The other app files (page, `curation.json`, manifest) are revalidated with the server, but a file already cached is served after 2 s (`SLOW`) on a slow link while the network refreshes the cache in the background.
- Speed on poor connections and low-end phones (Pierre, 2026-11-01; measured with `node tools/perf.js`, network × CPU profiles, and `node tools/perf.js field`, the field link below):
  - **Load order in tiers** (Pierre, 2026-11-02). A real RA's first visit from the IMR field station (HAR, Chrome) was served from Fastly's Manila POP (latency ~0.4 s, fine) but at ~86 kbit/s: at 0.5 s the page asked for everything at once (fonts, data.json, the 12 scripts, the Lab stylesheet and hub), each file got a sliver of the line and all came together at 20-25 s; then the service worker's install fetched the rest of the shell (Lab prototypes, fonts...) while the first quiz photo (960 px, 62 KB) came at 47 s. Now the files come one tier after the other, so what the player waits for never shares the line with the rest: **1 Home** (`app.css`, `proto/lab.css`, which also holds the layout of Home, My progress and the games' side columns (`.pgame`, `data-page=lab`), `home.css`, the main font, `core.js`, `app.js`, `sync.js`, `home-art.js`, `home.js`, `tour.js`, `data.json`, `curation.json`), **2 the photo quiz** (`model.js`, `tips.js` (the "Did you know?" tips' registry and rules, 3 KB), `quiz.js`, `learn.js`, which the quiz uses for its look-alike pairs and mix-up montages, `progress.js`, 13 KB, which each answer updates (achievements) and which opens My progress at once (Codex review #361: answers given before it lost their achievement bookkeeping, and a sign-in from the tour reached its record before it existed: the sign-in now waits for tier 2), with `forms.json`, `quality.json` and `picks.json`, which the draw and the photo slots use: the data is rebuilt with them, then the achievements are counted and the sheet's photo statistics asked for), **3 the photos of the next quiz questions** (planned at once, see Quiz below), **4 the sheet's reads** (sync, anonymous answers, leaderboard, achievement shares), **5 the rest** (`flag.js`, `proto/lab.js` with the Lab prototypes), then the service worker is registered: its install caches every other shell file (italic and condensed fonts, Lab...) for the next visit, which stays instant. Home's doors need data.json (the photo band), so Home waits for it; Home's own photos are lazy thumbnails. The tiers are listed in `index.html` (tier 1 as `<link rel=preload as=script data-tier=1>`, later ones as bare `<link data-tier=N href>`, which fetch nothing until the loader turns them into preloads); `loadTier(N)` in the inline loader starts tiers 2..N at once and resolves once their scripts have run, in order; `need(N)` in `app.js` adds each tier's set-up (`SETUP`) and `HAVE` is the last tier in. A page opened before its files arrived (`pageTier`: Home 1; quiz, duels, Learn pages, My progress, leaderboard and achievements 2; Tools and Coral ID Key 5) shows the loading bar and asks for its tier at once, ahead of the queue (`route()`); a link straight to a page asks for its tier at start-up, alongside Home's files. `window.APP_READY` is set once tier 2 is in (Home, the quiz and the Learn pages work); `window.ROUTED` holds the address of the last page `route()` drew (tests wait for it instead of a fixed time). Field link, phone, first visit (`tools/perf.js field`, one run each, so a few seconds of noise), before → after: Home shown 37.3 → 20.9 s (387 → 213 KB before it), first quiz photo when the player goes straight to the quiz from Home 69 → 38 s from the start, Next → photo for questions 2-5 22/24/7/25 → 10/12/0/0 s, My progress 37 → 28 s from the start (tap on Home), first quiz photo after 30 s on Home 29 → 6 s after the tap. On a desktop, Home also comes at 21 s instead of 37 s, and with Saver taking the 480 px file whatever the box the first quiz photo comes +18.6 s after the tap instead of +37.8 s, Next → photo for questions 2-5 4/5/0/9 s instead of 35/21/22/27 s. A photo-quiz question that changes what comes next (an exam question, a slipped-in duel, an "Again", cards) is answered before anything is planned past it (Codex review #361: an exam planned behind an unanswered exam broke its spacing).
  - Start-up never waits for `curation.json` when a kept copy exists (`CUR_KEPT`); `curRefresh` reads it right after, and a change applies at the next screen.
  - Quiz: the next questions are chosen ahead, up to 3 in the photo quiz (`AHEAD`; one in the Duel tab), and their photos fetched meanwhile, so Next shows one at once (`planNext`, `NEXTQ` holding the next ones in `.next`, each keyed on the answers count it is for and the genera in play; Pierre, 2026-11-02: a fluent RA answers in ~8 s, less than one question's photos take at 86 kbit/s, and 95% of the answers are in the photo quiz). The queue is topped up when a question shows and after each answer. Planning ahead keeps the rules of the draw: a question with cards, an exam question, a duel slipped in or an "Again" ends the queue (nothing is chosen past it before it is played), and a wrong answer drops the queue, putting the planner's own state back (`dropPlans`: genus asked last, duel and "Again" spacing), so the "Again" still comes one question later. After a right answer the questions already chosen stay: their weights lag up to 2 answers, and a new card, exam question or duel can come up to 2 questions later than without planning ahead. The photos come in order of need, two at a time, question after question (cards of the genera met, then the photos shown small then full size, then hint and other views; `pump`, with `fetch()`, which unlike `new Image()` does not hold the page's load event): all at once they shared a slow line and the first photo came later than without preloading. The first questions are planned as soon as tier 2 is in.
  - Start-up on an unstable line: the JSON files are fetched again on failure, up to 3 tries (`getR`); each tier's scripts are preloaded (downloaded in parallel) and run in order by an inline loader in `index.html` (its own CSP hash), each failed one tried again up to 3 times; `window.BOOT` resolves once tier 1 has run, and app.js waits for it before the first page (`domReady`). A failed stylesheet is tried again the same way, and so are the Lab prototypes (`labLoad`). data.json is preloaded too (`as=fetch crossorigin`, same URL as the fetch, so it downloads alongside the scripts). Under "Loading…" a bar moves one step per script run and one for data.json (`bootTick`; it counts tier 1, or the tiers the first page needs: `bootMax`), and after 6 s a line says only the first visit is this slow (beginner RA review, 2026-11-02: 5-8 s of a bare "Loading…" at 400 kbps looked stuck). If data.json still fails, the page offers Try again. A first version reloaded the whole page on a failed file: on a line failing 1 request in 5, every reload failed again. Before, one failed request among ~10 start-up files left the app on Loading for good (`tools/perf.js`, 1 request in 5 failing, no service worker yet).
  - Pages: leaving a page drops its photos still loading (`route()`), so a slow line goes to the new page.
  - Photo sizes (Pierre, 2026-11-01): each photo exists in 1600, 960 (`-m`), 480 (`-s`) and 240 px (`-t`). A big photo (quiz, Look-alikes, sheet cover, lab tools) gets the smallest file that covers its box at the screen's density counted up to 2x (`fit`); the quiz guesses the box from the last question with as many photos (`QBOX`, so the preload fetches the right file), and a box bigger than guessed loads the bigger file (`upsizeImg`, `upsize`, never smaller). Cards and strips use `srcset` with the 480, 960 and 1600 px files (card `sizes` measured per S/M/L setting). Thumbnails (home band, progress tiles, look-alike pairs, tips) use `thumb()`: 240 or 480 px by drawn width and density (a home tile on a phone is ~60 px: 240 px, ~10 KB, instead of 480 px, ~30 KB). The home ReefCloud art has a 760 px version for phones. Leaving a page drops `srcset` with `src`, or the download goes on. The enlarged view loads the 1600 px file over the 480 px one. A photo not downloaded yet (`r: 1`: a candidate just added, and all of Millepora's game photos, `DATA.x.gen`) loads from iNaturalist with two files only (`img()`): `medium` (500 px) for the 480 px size, `large` (1024 px) for 960 and 1600 px; `resized()`, `upsizeImg` and the preload (`pfUrls`) leave it alone. A quiz photo carries its name in `data-f` (`quiz.js` `question`), so the failed-photo report (`ev('photo')`, admin "Photos not loaded") and the tests (`net.smoke.js`, `profiles.smoke.js`, `tools/perf.js`) name an iNaturalist photo by its `f`, not by its URL.
  - Photo quality setting (`reefid-photo-q`): Auto (default), Saver, Full. Saver takes the 480 px file for a big photo whatever its box (shown whole at its own size on a bigger desktop box, LOWRES; field link: at 1x a desktop quiz box still took the 960 px file, two per question), drops the 1600 px file from `srcset`, gives thumbnails their 240 px file and Home's ReefCloud art its 760 px one (field link: Home's photos on a desktop came to ~600 KB), and the enlarged view starts at 960 px (1600 on a click). Auto is Saver when the browser reports the data saver or a 2g/3g connection (Network Information API, Chrome on Android), or, once the app has measured the line itself, when it is under 500 kbit/s (Pierre: 480 px photos on a 1080p or 4K desktop are a real loss; the browser's estimate only counts before a measure; `linkMeasure`, `LINK`: the bytes the page got from the network over the time spent receiving them, Resource Timing, overlapping downloads counted once, cached files not at all, once 40 KB are in; kept in `reefid-link` for a launch served from the cache). Field HAR, 2026-11-02: at ~86 kbit/s Chrome's estimate did not flag the link, so Auto loaded the 960 px quiz photo (62 KB, 19 s); Safari and Firefox have no Network Information API. Saver never moves a shown photo to a bigger file (`upsizeImg`); only the enlarged view does, on a tap. Full always loads 1600 px for big photos.
  - Each game photo shows its 480 px version (`data-lo`, also the blurred backdrop) as the image's background until the bigger one is in.
  - A failing photo is retried twice (after 1 s, then 4 s), then replaced by its 480 px version. If that fails too, the frame shows the "photo missing" tile (`app.js` `noPhoto`, docs/DESIGN.md), the question's answers close, it offers another one, and nothing is counted. The whole chain for a site photo: R2 → R2 once more (800 ms) → its online original at a light size (or the site's `img/` for a photo with none) → 2 retries → the 480 px version (online `medium`, or R2's copy first under the service worker) → the tile. On a slow line (Saver) the files asked are already the 480 px ones (`fit`), so the online fallback is `medium` from the start.
  - The leaderboard and achievement shares are kept on the device (`reefid-board-cache`, `reefid-achs-cache`): drawn at once, then refreshed. They are fetched with tier 4, after the quiz and its next photos.
  - Fonts are served from `fonts/` (latin subset, SIL OFL), not Google Fonts.
- `privacy.html`: the privacy notice (static, no script, own CSP), linked from the ? help of every page and from About and credits (`#about`); also the privacy policy link of the Google Cloud project behind the sync script's self-update. Keep it true when the data stored changes (new Sheet column, new external host).
- Link preview (Pierre, 2026-11-01): `index.html` carries Open Graph / Twitter meta tags pointing at `og.jpg` (1200 × 630, six of Pierre's own photos + the app name), made by `node tools/og/make_og.js` from `tools/og/og.html`. Absolute URLs (crawlers need them); WhatsApp caches a preview per URL, so an old share keeps its old card.
- App icon (C1, chosen by Pierre on 2026-11-06: a loupe, dark glass with a white rim and glint, a coral fish and a green brain coral inside, a straight handle): `icon.svg` is the "any" icon, a rounded square (favicon of every page, the header logo, the Lab's placeholder, `og.html`); `icon-192.png` and `icon-512.png` are the same as PNG; `icon-maskable-192.png` and `icon-maskable-512.png` are the full-bleed art (motif inside the 80 % safe circle) for Android's masks; `apple-touch-icon.png` (180 px, full bleed, opaque) is the iOS home-screen icon (`index.html`, `admin.html`). `manifest.webmanifest` lists the SVG and the four PNGs. Only `icon.svg` is in `sw.js` `SHELL` (the PNGs are read by the system when the app is installed: no download for players at each new version); the deploy's `V` hashes `icon.svg` and the manifest, so a new icon reaches installed apps with the next version.
- Everything runs in the browser. The only backend is a Google Apps Script web app that stores RA progress in a Google Sheet.

## Data files

### `data.json` (served source of truth)
Layout (code re-review M5): written only by `tools/datajson.py` `dump()`: one top-level key per line, and one genus per line inside `gen`, `course`, `cand`, `x` and `x.gen` (compact JSON within a line, key order kept, trailing newline), so edits to different genera merge cleanly. `python3 tools/datajson.py` rewrites the file in that layout; `--check` (PR check) fails when it is not. The app only parses it, so the layout does not matter to it.
- `gen{Genus}`: `n` slate number, `fam`, `ig` IMR lecture group, `imr` lecture cues (verbatim), `qt` short ID tips, `sum` short description, `plain` the plain sentence (also on every `x.gen` record; below), `mn` mnemonic, `crit` Coral Finder criteria, `tr` trait ids, `trs` trait ids found in some species only (Pierre, 2026-11-04: e.g. paliform lobes in some Favites; every tool reads `tr` and `trs` through `proto/lab.js` `trHas` (1 / 0.5 some species / 0), `trAll`, `trLabel`, `trFits`, never by genus name: half a match in the Coral ID Key, never eliminated on in the Elimination board, an "In some species" row in the Feature gallery, a ring in the Feature matrix; `tools/apply_some_species.py`, `tests/traits.test.js`), `look` look-alikes + `lsrc` source per pair, `pages` CF pages, `sl`/`rsl` slide numbers, `info` dated "Other sources" notes, `check` points to check with a trainer, `levels` (2 or 3 views), `views{wide,medium,macro}` photo lists, `more` extra photos, `book` Coral Finder book crops, `cover`, `cm` how common the genus is near Dauin (a small integer, the geometric mean of its iNaturalist observations and observers within 40 km; written by `tools/commonness.py`, also on the `x.gen` records of Millepora and the bonus genera; used by the opening of genera, docs/LEARNING.md "Common first").
- **The plain sentence** (Pierre, 2026-11-03: sheets clear for everyone, complete beginners included, divers who never had the IMR coral lecture; the scientific IMR text stays for the RAs): `plain` on each genus of `gen` and `x.gen`, 1-2 sentences of at most 30 words in everyday words (shape, texture, size, colour caveats, a comparison), shown in body text with no label right under the photo, before the ID tips and lecture notes: first in the text column of the genus sheet (`learn.js` `viewGenus`, `.idbox`; beside the photo on tablet and desktop) and under the name on the first-meeting card (`quiz.js` `introShow`), by `app.js` `plainLine()` (`.plainw`). It was first a muted "In plain words" line above the photo; Pierre's review the same day: people look at the photo first, then at what is under it, and skipped it. The lines are a synthesis in the app's own words (no sentence copied) of how field guides and references describe the genus underwater, each line checked against at least 2 of them (`tools/plain_sources.json`: Corals of the World factsheets, Reef Corals of the Indo-Malayan Seas, the ReefCloud hard coral genera guide, Wikipedia and a few others), plus our IMR lecture notes and ID tips and the genus's own photos; where a source differed from the IMR notes, the line followed the IMR notes, except four IMR wordings Pierre had corrected after the sources (2026-11-03, `tools/apply_imr_corrections.py` for the lecture notes, mnemonic, `sum` and the old "to check" note, `tools/id_tips.txt` for the ID tips; reasons and quotes in the script and in `plain_sources.json` `_corrections`): Seriatopora corallites "in neat rows", no longer "black", and its mnemonic "Serius Black" replaced by the name itself (Latin *seriatus*, in rows: "Seria-topora": pores in series); Lobactis tentacular lobes "often green, blue or white", not "pale" (Corals of the World); Heliofungia tentacle tips "white or pink"; Herpolitha "free-living like a mushroom coral, but many mouths along the furrow" (the IMR "solitary" and the Coral Finder's "colonial" both hold: one disc, many mouths; Hoeksema 1989 says monostomatous / polystomatous instead), its "to check" note now an "Other sources" note; the glossary's Solitary says the same. Written by `tools/apply_plain_sheets.py`. `tests/plain.test.js`: every genus has one, within the limit; no 5-word run taken from the Coral Finder features; 2+ sources each; a slate genus's line names another genus only when its card comes after that genus's (`starRefs`). `tests/pages.smoke.js` checks that a sheet and the first cards show it after the photo, before the tips, with no label.

## Security model

What is public, what protects what (code review, 2026-11-01).
- **Everything in the repo is public**, including the admin page code and the sync URL. The admin password only unlocks the token stored in that browser; it protects nothing on its own.
- **The GitHub token is the real key**: fine-grained, this repo only, Contents read/write, 90-day expiry. Kept encrypted in `localStorage` (`reefid-admin-vault`); the unlocked token lives in `sessionStorage` only. `ppericard.github.io` is shared by every Pages site of the account, so never add third-party scripts: the CSP (`<meta http-equiv="Content-Security-Policy">` in `index.html` and `admin.html`) allows scripts from this site only, inline scripts by hash (`tests/csp.test.js` fails if a hash is stale). Add a host to `img-src` / `connect-src` there when a new external source is needed. `admin.html` also allows `https://www.fishbase.de` in `img-src` (the FishBase fish candidates, shown remote; `tests/csp.test.js` checks every candidate host is allowed). The R2 bucket (`https://pub-934250f83b884a4f890497f2027ce251.r2.dev`) is in `img-src` (the photos) and `connect-src` (any `fetch()` of a photo; the service worker's own requests follow no page CSP).
- **Templates**: every data string goes through `esc()` (escapes `& < > " '`); links from data go through `safeUrl()` (https only).
- **Sync sheet**: anyone can call the Apps Script URL. A name + 4-digit code only prevents accidental overwrites; v6 throttles wrong codes, never writes a user string as a formula, and keeps anonymous ids unguessable (secret salt). RA data is low-sensitivity (first names and quiz answers).
- **GitHub Action** (`approved-photos.yml`, `contents: write`): downloads photos only from iNaturalist hosts (`tools/fetch_approved.py` `HOSTS`).
- **Photos to R2** (`photos-r2.yml` and the last job of `approved-photos.yml` (its `r2` job), `tools/r2_sync.sh`; Pierre, 2026-11-03; both in the concurrency group `photos-r2`): `img/` copied to the Cloudflare R2 bucket (public address `https://pub-934250f83b884a4f890497f2027ce251.r2.dev`, CORS for the site and localhost) with rclone (the official release, pinned to one version in `tools/r2_sync.sh` and checked against its SHA-256 before it runs; never the runner's apt package) and an R2 API token limited to that bucket (Object Read & Write), from the repo's secrets; files compared by checksum; **nothing is ever deleted from the bucket** (`rclone copy`, since step 2: the photos with an online original live there only), and the run fails if an R2-only photo lacks one of its four files. The `photos` job of `approved-photos.yml` uploads the photos `tools/fetch_approved.py` downloaded (`tools/r2_sync.sh r2-upload`, which fails without the secrets) before its commit. The app and the admin read the photos from the bucket ("Photos").

## Run and deploy

- Run: `python3 -m http.server 8000` at the repo root, open <http://localhost:8000> (`admin.html` for the back-office; without a token use `admin.html?demo`, made-up data, or `admin.html?readonly`, the real public curation). Sync and photo Elo talk to the live Apps Script even locally.
- Deploy: `.github/workflows/pages.yml` publishes current `main` as a static artifact, with one `pages` concurrency group and `cancel-in-progress: true`. Settings > Pages must use **GitHub Actions**; the workflow fails early while the legacy branch source is selected. Migration, incident evidence and CLI recovery: [PAGES.md](PAGES.md).
- Pierre's Publish pushes `curation.json` to `main`, triggering both Deploy Pages and Candidate photos. The latter commits `data.json`/`img` using `GITHUB_TOKEN`; its completion triggers Deploy Pages again so bot changes are published too.
- The service worker serves the cached shell: the deploy stamps every `?v=` and `sw.js` `V` from content hashes (`tools/stamp_versions.py`, rule W15), so a shell change reaches the players without anyone bumping a number. `curation.json` is fetched with `no-cache` (from the kept copy first at start-up, see above).
- A completed Actions run can leave a stale Pages backend lock. Cancel the blocking **Pages deployment** as well as any stuck Actions run, then dispatch `pages.yml` on `main`; see [PAGES.md](PAGES.md#manual-recovery). Repeatedly rerunning the blocking legacy SHA is not the fix.

## Players' reports (2026-11-01)

In every game (Quiz, Custom quiz, Look-alike duels, Memory, Reveal), once the answer is out, the feedback shows a discreet "⚑ Report a problem" (`repBtn()` in `sync.js`; Lab games call it if present). It opens a small dialog (`reportDialog()`): Wrong answer (with a "Right genus, if you know" field, suggestions from the 39 genera), Several corals, Bad photo, Other (in the current subject's words, `SUBJECTS` `one` and `name`: with Fish on, "Right family, if you know" with the entries' IMR names, never their teaching ids, and "Several fish"), an optional note, and "Your name" when the player is not signed in to the sync. A report carries the photos of the question (one observation), the expected genus, the answer given and the game. Reports queue in `localStorage` `reefid-reports` and are sent by `sendReports()` (on send, start-up and when back online) to `Code.gs` v7; an older script leaves them queued. Admin To do (views All and Reports; script v8) lists them first ("Reports and feedback", `renderTriage` `repCard`), with the reporter's name (a `?` after it = not verified by a sync code), each photo with every tool of its genus page, and ✓ Done per report (`seen['rep:id']`). Since v8 the same dialog also opens from "⚑ Report" in the caption of any enlarged photo (lightbox, not while a game hides the genus; reasons Wrong genus, Several corals, Bad photo, Other), "⚑ Report a problem with this sheet" at the bottom of a genus sheet (Wrong information, Bad photo, Other) and "Send feedback" at the end of the ? help of every page and on About and credits (Wrong information, Bug, Suggestion, Other; a page footer until 2026-11-03); `REP_WHY[kind]`, and every report carries the page it came from (`w`, sheet column `Where`). Nothing is ever changed automatically from a report. Pierre's own ⚑ flag (`flag.js`) is separate and stays admin-only.
