# Architecture

How the app is put together. Rules and workflow are in [`../AGENTS.md`](../AGENTS.md); deferred ideas in [`ROADMAP.md`](ROADMAP.md).

## Overview

```
data.json (genus data + photo lists) ──┐
forms.json / quality.json / picks.json ├─> app.js (applyCuration + applySlots from core.js, applyForms) ─> pages
curation.json (Pierre's choices) ──────┘                                    │
                                                                            └─> progress in localStorage ─> Apps Script ─> Google Sheet
admin.html ──(GitHub Contents API, Pierre's token)──> curation.json on main ──> GitHub Action fetches approved photos
```

- Static site served by GitHub Pages from `main` via `pages.yml` (Actions source; migration and recovery in [PAGES.md](PAGES.md)). No framework, no bundler, no npm.
- A service worker (`sw.js`) caches the app shell for offline use (versioned cache `V`, replaced on each deploy) and photos as they are viewed, in a separate cache `imr-photos-v1` that deploys never delete (capped at 2,500 entries, only good replies kept). `curation.json` is part of the shell, so the first offline launch after a deploy still has Pierre's choices; the app also keeps the last curation it read in `localStorage` (`imr-curation-last`) as a fallback. The install fetches each shell file on its own, up to 3 tries (with `addAll`, one failed request on an unstable line failed the whole install). Versioned files (`?v=` in the URL) and `fonts/` are cache-first (a new version is a new URL), so a launch needs no network once cached. The other app files (page, `curation.json`, manifest) are revalidated with the server, but a file already cached is served after 2 s (`SLOW`) on a slow link while the network refreshes the cache in the background.
- Speed on poor connections and low-end phones (Pierre, 2026-11-01; measured with `node tools/perf.js`, network × CPU profiles):
  - Start-up never waits for `curation.json` when a kept copy exists (`CUR_KEPT`); `curRefresh` reads it right after, and a change applies at the next screen.
  - Quiz: the next question is chosen while the feedback is read, and its photos are fetched meanwhile (`planNext`, `NEXTQ`, keyed on the answers count and the genera in play). The photos come in order of need, two at a time (shown photos small then full size, then hint and other views): all at once they shared a slow line and the first photo came later than without preloading. The first question is planned 2.5 s after start-up.
  - Pages: leaving a page drops its photos still loading (`route()`), so a slow line goes to the new page.
  - Photo sizes (Pierre, 2026-11-01): each photo exists in 1600, 960 (`-m`) and 480 px (`-s`). A big photo (quiz, Look-alikes, sheet cover, lab tools) gets the smallest file that covers its box at the screen's density counted up to 2x (`fit`); the quiz guesses the box from the last question with as many photos (`QBOX`, so the preload fetches the right file), and a box bigger than guessed loads the bigger file (`upsizeImg`, `upsize`, never smaller). Cards and strips use `srcset` with the three files. The enlarged view loads the 1600 px file over the 480 px one.
  - Photo quality setting (`imr-photo-q`): Auto (default), Saver, Full. Saver counts 1x (about one size down: 480 px for a phone quiz photo), drops the 1600 px file from `srcset`, and the enlarged view starts at 960 px (1600 on a click). Auto is Saver when the browser reports the data saver or a 2g/3g connection (Network Information API, Chrome on Android; elsewhere Auto sizes by box). Full always loads 1600 px for big photos.
  - Each game photo shows its 480 px version (`data-lo`, also the blurred backdrop) as the image's background until the bigger one is in.
  - A failing photo is retried twice (after 1 s, then 4 s), then replaced by its 480 px version. If that fails too, the question offers another one, and nothing is counted.
  - The leaderboard and achievement shares are kept on the device (`imr-board-cache`, `imr-achs-cache`): drawn at once, then refreshed. They are fetched 2.5 s after start-up.
  - Fonts are served from `fonts/` (latin subset, SIL OFL), not Google Fonts.
- `privacy.html`: the privacy notice (static, no script, own CSP), linked from the footer; also the privacy policy link of the Google Cloud project behind the sync script's self-update. Keep it true when the data stored changes (new Sheet column, new external host).
- Link preview (Pierre, 2026-11-01): `index.html` carries Open Graph / Twitter meta tags pointing at `og.jpg` (1200 × 630, six of Pierre's own photos + the app name), made by `node tools/og/make_og.js` from `tools/og/og.html`. Absolute URLs (crawlers need them); WhatsApp caches a preview per URL, so an old share keeps its old card.
- Everything runs in the browser. The only backend is a Google Apps Script web app that stores RA progress in a Google Sheet.

### Learning model (`app.js`)
- Per-genus state in `localStorage` `imr-coral-progress` (`P[genus]`: `ok`, `ko`, `h` recent results string, `L` BKT, `th` ability, `ps` photos seen `{f: [seen, right]}`, `ro` recent colonies, `cor`/`du` milestones).
- **Learned** = the **silent mastery exam** passed (`s.mx`; Pierre, 2026-11-01: "an ultimate test from 95% to 100%"; the former two milestones, right once with the corallites in view and once in a duel, were dropped as easy and arbitrary). Bayesian Knowledge Tracing (`BKT`, `bktStep`, `knownP(n)`) fills a genus up to 95%; once `knownP` ≥ 0.95 (`examOn`), `EXAM.n` = 5 questions on it are slipped unannounced into the photo quiz (`quizPhoto` → `examSet`), at least `EXAM.gap` = 8 answers apart (`examReady`, counted in answers, never time; `weight()` raises a genus ready for its next exam question to 3 and holds it back in between): one photo alone, never answered right before (else the least seen), the hardest of its view, the views taking turns (`s.ex = {k, v, at}`), 3 look-alike traps. All right: `s.mx = 1` and a pop-up; mastery is kept while the genus stays at 95% (misses that bring it under, for the genus shown or the one answered, take it away and bring the exam back). Exam photos are never-shown ones first. The exam's count is shown nowhere (Pierre: only the genus's %, which creeps up from 95% and falls back on a miss, keeps the mystery). Any miss on the genus (exam or not) and any time it is given as the answer for another genus drops `s.ex`; it starts again when L is back at 95%. `mergeProgress` takes `mx` and `ex` from the device that played, like `L`. `tests/draw.smoke.js` plays an exam through the real quiz. Guess and slip depend on the photo's difficulty, so right answers on hard photos count most. **Review** = 2+ misses in the last 5 results. **No time criteria anywhere** (rule).
- A wrong answer is a failed observation for the genus shown **and** the genus given (rule).
- **Progress scale**: `genScore` = 0.95 × BKT progress towards 0.95, + 1% per exam question passed, 1 once mastered; `lvStep` = 6 steps (0 not seen, 1-4 quarters of `genScore`, 5 learned) coloured by the palette's learning-level ramp; tiles on My progress (Photos / Slate / Groups views) show a mini ring + %; review = red border and "!" (dashed in colour-blind mode). `progPct` drives the header ring.
- **Which genus next**: `weight()` favours unseen (10), review and unsure genera, learned 0.25, and holds back the last 4 genera asked. Bonus genera weigh at most `BONUS_W` = 4 (as a genus being learned, even when new or to review), and all of them together at most `BONUS_SHARE` = 15% of the draw (`weighted()` scales them down; Pierre, 2026-11-01, after a burst of bonus questions right after unlocking some: simulated 34% before, 15% after).
- **Continuous difficulty** (Elo as in Pelánek 2016; PRs #197, #200): per-genus ability `P[n].th` on the photo-difficulty scale, updated by `abilityStep()` with P(right) = g + (1-g)·sigmoid(ability − difficulty), g = 1/choices, K shrinking with answers but ≥ 0.25 (`ELO`). **Global level** (Pierre, 2026-11-01: strong beta testers must not wait ~100 questions for traps): the same Elo step runs over every answer into the pseudo-genus `P['~level']` (`LEVEL` in `core.js`; ok, ko, th like a genus, so it syncs and merges like one, and appears in the sheet's per-genus abilities under that key). A genus never answered starts from `playerStart(P, n)` (`core.js`): 0.8 × global ability × M/(M+10) (M = its answers), clamped to [−0.5, 1.5] (`START`); progress saved before falls back on the answer-weighted mean of the genera's abilities, and the record is made at the next answer from that history (`levelSeed()`: all answers so far, that mean), so an existing player's earlier answers keep counting. Taken once: the first answer saves the genus's own `th`. Simulated (real `photoSet`/`distractors`, all right): traps over the first 25 questions 1.9 on average instead of 0.1, 2.8 over questions 26-50 instead of 0.5; a player at 50% stays at 0 traps, starting new genera at −0.5. Learned (BKT) is not carried over: each genus is still proven by its own answers. `photoSet()` draws photos weighted around the target `ability − 1.0` (~80% right in a 4-choice question, `PICKD`), with a bonus for never-seen photos (IMR and Pierre's first), photos answered right twice down-weighted, the last colonies held back and ≥ 3 colonies in rotation (`VARIETY`). **Answer choices** (Pierre, 2026-11-01) follow the same ability: `trapsFor(t)` = how many of the 3 wrong choices are look-alikes of the target (`look` both ways), 0 on a genus's first question (ability 0), then +1 per 0.18 (`TRAP`), randomly rounded in between, all 3 from 0.54: one look-alike after the first right answer, all three after about 5, because they are how genera are learned (Pierre, 2026-11-01). While traps are 0-1 the other wrong choices are genera sharing no IMR growth form with the target (`imrFormsOf`), other lecture groups first and each in a different growth form (so the answer is not the odd one out); from 2 traps the last choice is family first, then any genus (the old rule). With 0-1 trap, Elo and BKT use g = 1/k with k = target + plausible wrong choices (`plausibleK()`: look-alikes or a shared growth form, min 2), and the answer log records the mode as `quiz|kN` so the sheet's `stats_` (Code.gs v9) and `eloOf()` (`core.js`) rate the photo with the same guess rate; an older sheet script treats it as 4 choices. **Confusion scores** (Pierre, 2026-11-01: real mix-ups are more relevant than the declared look-alikes alone, which only initialise them): the look-alike traps are the genera with the highest `confOf(t, n)` = `confScore()` (`core.js`): mixed up / offered together for the pair, pooled over every RA (`?stats=1` `conf`, Code.gs v10), starting from a prior worth `CONF.W` = 8 offers (declared look-alike 0.3, same family 0.12, shared IMR growth form 0.08, other 0.03). A pair is a trap (`confusable`) from `CONF.TRAP` = 0.2, so a declared pair nobody confuses fades and an undeclared one players do confuse becomes a trap; scores are shuffled ±20% so close pairs all get tried. `plausibleK()` counts confusable choices. Every answer logs the choices offered (`ch`, Code.gs v10 `Choices` column); without v10 deployed `conf` is empty and the priors alone apply (the old behaviour). **Personal path** (Pierre, 2026-11-01): that pooled score is then the prior for the player's own record on the pair, `pairConf(P, a, b)` (`core.js`) = [offered together, mixed up] in both directions from `P[g].off` (each wrong choice shown beside `g`, counted in `answer()` since 2026-11-01) and `P[g].conf` (genus answered instead), again worth `CONF.W` offers, so the player's weight is offers / (offers + 8). A pair a player keeps mixing up becomes their trap even if others don't confuse it; one they now tell apart sinks back. Duels weigh pairs ×3 when the player mixed them up and still confuses them, ×2 when `confusable` or a classic, else ×1. My progress "Often mixed up" lists the player's mixed-up pairs ranked by that score (top 3, chips open the comparison with "Drill this pair"). `mergeProgress()` adds `off` up across devices like `conf`.
- **One colony per question** (PR #207, rule 14b): photos are grouped by observation (`p.o`); a question shows the views of one colony only, never topped up from another. Beginners favour colonies shot at several zooms; `singleP()` raises the share of single-view questions (up to 85%) as ability rises; a single view counts as +0.5 harder (`SINGLE`). Other views show after the answer.
- **Bonus genera** (Pierre, 2026-11-01; `BONUS`, `BONUS_AT`, `bonusOpen()`, `isBonus()`): 6 extra Dauin genera (`DATA.x.gen`) join the photo quiz and the duels as the player progresses: Millepora, Isopora, Leptoseris, Heliopora, Sandalolitha, Pleuractis, in that order. Chosen as: 4+ Research Grade iNat observations within 40 km of Dauin, and a slate look-alike named by the Coral Finder (`look`/`lsrc`), or not a hard coral (Heliopora). The first unlocks at 10% slate progress (`progPct`), then one more per 5%; unlocked stays unlocked (`imr-coral-quiz` `Q.bu`; `Q.ba` = how many were announced in the quiz feedback). They are choices and distractors like slate genera (`distractors()` matches look-alikes both ways), duel with their slate look-alike, have their own `P[n]` (synced), and count as "wrongly given" (rule 13); they never count in the slate progress (`progPct`, the 39 tiles, the sync summary). My progress shows them after the slate genera in all three views (photo wall: tiles tagged "Bonus"; Slate: a strip under the slate; Groups: a "+" row), locked ones as ONE "+N bonus genera · next at X%" tile (designer re-review 2026-11-01). Each unlock opens an animated card once (`unlockShow()`: a "?" tile turns over to the cover photo, name and Coral Finder tips; no motion with `prefers-reduced-motion`). ID tips are labelled "ID tips (Coral Finder p. …)", never IMR. `#cmp-A|B` accepts bonus genera (with a slate genus or each other). A two-level bonus genus counts its `medium` photos as close-ups in games (Sandalolitha). Game photos: Research Grade only (`p.gid` = not Research Grade, set by `tools/apply_bonus.py`), Pierre's own always, never multi-coral. Memory (Lab `pairs`) does not use them.
- **Photo difficulty** `photoDiff()`: the sheet's photo Elo (`?stats=1`, all players, cached in `imr-photo-stats`) shrunk towards a prior from the photo's game set (Easy −1, Medium 0, Hard +1) when it has few answers. The admin "Without me" switch recomputes it without Pierre's answers for Stats only; the games still use everyone's.

## Data files

### `data.json` (served source of truth)
Layout (code re-review M5): written only by `tools/datajson.py` `dump()`: one top-level key per line, and one genus per line inside `gen`, `course`, `cand`, `x` and `x.gen` (compact JSON within a line, key order kept, trailing newline), so edits to different genera merge cleanly. `python3 tools/datajson.py` rewrites the file in that layout; `--check` (PR check) fails when it is not. The app only parses it, so the layout does not matter to it.
- `gen{Genus}`: `n` slate number, `fam`, `ig` IMR lecture group, `imr` lecture cues (verbatim), `qt` short ID tips, `sum` short description, `mn` mnemonic, `crit` Coral Finder criteria, `tr` trait ids, `look` look-alikes + `lsrc` source per pair, `pages` CF pages, `sl`/`rsl` slide numbers, `info` dated "Other sources" notes, `check` points to check with a trainer, `levels` (2 or 3 views), `views{wide,medium,macro}` photo lists, `more` extra photos, `book` Coral Finder book crops, `cover`.
- Photo object: `f` file stem in `img/`, `ar` width/height (quiz layout; `r: 1` means remote, see below), `a` attribution, `lic`, `o` original URL, `t` taxon, `own` (Pierre's), `loc` (dauin/ph/world), `src` remote URL when not downloaded (`r: 1`), `gid: 1` when the iNat observation is not Research Grade (candidates; bonus genera, kept out of games).
- `cand` = only the candidates `curation.json` names (the ones Pierre added, moved or sent to another genus: the app needs them to apply the curation). The candidates still waiting live in **`cand.json`** (same layout, top key `cand`; Pierre, 2026-11-01: a big backlog must not weigh on every player's download): only the admin loads it (and the app's `?draft` preview). Tools read both with `datajson.load_all()` and write back with `dump_all()`, which re-splits by what `curation.json` names; One-off backlog runs: `python3 tools/fetch_local.py --dauin 30 --ph 20 --ph-all` (raised caps, Philippines for every genus; first run 2026-11-01: 544 → 1825 photos waiting, 1321 observations; Caulastraea, Acanthastrea, Leptastrea, Stylocoeniella and Zoopilus still have none). `python3 tools/datajson.py --split` re-splits by hand, `--check` checks both layouts (CI).
- `key` Coral Finder front-page key (growth form → boxes), `imrg` the 11 IMR lecture groups, `traits` corallite clues with sources, `terms` glossary `[term, definition, source]`, `tips` the lecture's observation questions, `course` lecture photos, `cmp` lecture comparison images, `cand{Genus}` candidate photos for the admin, `x` extra Dauin genera for the Coral Finder and the bonus genera (built by `tools/build_extra.py`; `tools/apply_bonus.py` re-checks Research Grade and moves multi-coral photos of the bonus genera to `more`).

### `curation.json` (Pierre-owned; never overwrite in a PR)

## Security model

What is public, what protects what (code review, 2026-11-01).
- **Everything in the repo is public**, including the admin page code and the sync URL. The admin password only unlocks the token stored in that browser; it protects nothing on its own.
- **The GitHub token is the real key**: fine-grained, this repo only, Contents read/write, 90-day expiry. Kept encrypted in `localStorage` (`imr-admin-vault`); the unlocked token lives in `sessionStorage` only. `ppericard.github.io` is shared by every Pages site of the account, so never add third-party scripts: the CSP (`<meta http-equiv="Content-Security-Policy">` in `index.html` and `admin.html`) allows scripts from this site only, inline scripts by hash (`tests/csp.test.js` fails if a hash is stale). Add a host to `img-src` / `connect-src` there when a new external source is needed.
- **Templates**: every data string goes through `esc()` (escapes `& < > " '`); links from data go through `safeUrl()` (https only).
- **Sync sheet**: anyone can call the Apps Script URL. A name + 4-digit code only prevents accidental overwrites; v6 throttles wrong codes, never writes a user string as a formula, and keeps anonymous ids unguessable (secret salt). RA data is low-sensitivity (first names and quiz answers).
- **GitHub Action** (`approved-photos.yml`, `contents: write`): downloads photos only from iNaturalist hosts (`tools/fetch_approved.py` `HOSTS`).

## Run and deploy

- Run: `python3 -m http.server 8000` at the repo root, open <http://localhost:8000> (`admin.html` for the back-office; without a token use `admin.html?demo`, made-up data, or `admin.html?readonly`, the real public curation). Sync and photo Elo talk to the live Apps Script even locally.
- Deploy: `.github/workflows/pages.yml` publishes current `main` as a static artifact, with one `pages` concurrency group and `cancel-in-progress: true`. Settings > Pages must use **GitHub Actions**; the workflow fails early while the legacy branch source is selected. Migration, incident evidence and CLI recovery: [PAGES.md](PAGES.md).
- Pierre's Publish pushes `curation.json` to `main`, triggering both Deploy Pages and Candidate photos. The latter commits `data.json`/`img` using `GITHUB_TOKEN`; its completion triggers Deploy Pages again so bot changes are published too.
- The service worker serves the cached shell, so bump `?v=` numbers and `sw.js` `V` (see AGENTS.md) for shell changes. `curation.json` is fetched with `no-cache` (from the kept copy first at start-up, see above).
- A completed Actions run can leave a stale Pages backend lock. Cancel the blocking **Pages deployment** as well as any stuck Actions run, then dispatch `pages.yml` on `main`; see [PAGES.md](PAGES.md#manual-recovery). Repeatedly rerunning the blocking legacy SHA is not the fix.

## Players' reports (2026-11-01)

In every game (Photo → genus, Look-alike duels, Memory, Reveal), once the answer is out, the feedback shows a discreet "⚑ Report a problem" (`repBtn()` in `app.js`; Lab games call it if present). It opens a small dialog (`reportDialog()`): Wrong answer (with a "Right genus, if you know" field, suggestions from the 39 genera), Several corals, Bad photo, Other, an optional note, and "Your name" when the player is not signed in to the sync. A report carries the photos of the question (one observation), the expected genus, the answer given and the game. Reports queue in `localStorage` `imr-reports` and are sent by `sendReports()` (on send, start-up and when back online) to `Code.gs` v7; an older script leaves them queued. Admin Triage (script v8) lists them first ("Reported by players", `renderTriage` `repCard`), with the reporter's name (a `?` after it = not verified by a sync code), each photo with every tool of its genus page, and ✓ Done per report (`seen['rep:id']`). Since v8 the same dialog also opens from "⚑ Report" in the caption of any enlarged photo (lightbox, not while a game hides the genus; reasons Wrong genus, Several corals, Bad photo, Other), "⚑ Report a problem with this sheet" at the bottom of a genus sheet (Wrong information, Bad photo, Other) and "Send feedback" in the footer of every page (Wrong information, Bug, Suggestion, Other); `REP_WHY[kind]`, and every report carries the page it came from (`w`, sheet column `Where`). Nothing is ever changed automatically from a report. Pierre's own ⚑ flag (`flag.js`) is separate and stays admin-only.
