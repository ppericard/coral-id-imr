# Architecture

How the app is put together. Rules and workflow are in [`../AGENTS.md`](../AGENTS.md); deferred ideas in [`ROADMAP.md`](ROADMAP.md).

## Overview

```
data.json (genus data + photo lists) ──┐
forms.json / quality.json / picks.json ├─> app.js (applyCuration + applySlots from core.js, applyForms) ─> pages
curation.json (Pierre's choices) ──────┘                                    │
                                                                            └─> progress in localStorage ─> Apps Script ─> Google Sheet
admin.html ──(GitHub Contents API, Pierre's token)──> curation.json on main ──> GitHub Action fetches approved photos
```

- Static site served by GitHub Pages from `main` via `pages.yml` (Actions source; migration and recovery in [PAGES.md](PAGES.md)). No framework, no bundler, no npm.
- A service worker (`sw.js`) caches the app shell for offline use (versioned cache `V`, replaced on each deploy) and photos as they are viewed, in a separate cache `imr-photos-v1` that deploys never delete (capped at 2,500 entries, only good replies kept). Photos from R2 (see "Photos") go through it too: asked in CORS mode whatever the page asked (an `<img>` asks no-cors, whose opaque reply cannot be checked and costs ~7 MB of quota each in Chrome; the bucket allows the site), looked up under both addresses (R2 and the site's `img/`, so photos cached before the switch stay offline), and when R2 fails the worker serves the site's copy itself (`photo()` in `sw.js`). `curation.json` is part of the shell, so the first offline launch after a deploy still has Pierre's choices; the app also keeps the last curation it read in `localStorage` (`imr-curation-last`) as a fallback. **New versions reach players without a manual reload** (Pierre, 2026-11-02): each deploy changes `sw.js` (`V`), which the browser checks at each launch and the app re-checks when it comes back into view (5 min apart) and every 30 min (`swCheck`); the new worker installs in the background and takes over (`skipWaiting`, `clients.claim`), and the page then reloads itself when it next comes into view or at the next page change (`UPDATED`, `route()`), never in the middle of a page. A page from before 2026-11-03 has none of this (Pierre: RAs who opened one of the very first versions kept it open for days, so their answers never reached the sheet): on activate, the new worker asks each open app page (`index.html`) its version (`imr-ver?` over a `MessageChannel`, answered by `app.js`); a page that does not answer within 3 s is reloaded by the worker (`client.navigate`) onto the new version, once. Every request to the sheet carries the app's version (`av`, sheet v25), and the sheet logs one without it in Events as kind `old` (with the name or anonymous id it carries), so such devices can be found. The admin page does the same (`admin.js`, every click is already in the draft; not while the draft could not be saved). Both listen for the takeover (`controllerchange`) from their first line: the admin used to add its listener at the end of `start()`, after `data.json` and `cand.json`, and a version that took over meanwhile (a new worker waits for the old one's fetches still in flight, then takes over once the old one is idle) went unseen, so that tab kept the old code. The takeover can come later (Chromium, 2026-11-03, from timestamps of both workers and Chromium's `content/browser/service_worker`): a busy old worker is stopped the moment it is idle, and a request that comes while it stops (the page's next file or photo) starts the old version again, which is then not asked to stop early: the new version waits until the old one has been idle 30 s, or at most 5 min after its `skipWaiting()` (Chromium's "lame duck" timer; with DevTools attached, as in Playwright, only that). It happens when a new version finishes installing while the page still loads (a launch right after a deploy, photos held ~1 s by the R2 retry): the player gets the new version later, never not at all. `tests/net.smoke.js` check 9 publishes each version while its page is quiet. Before, a slow line served the old cached page after 2 s, so it took one or two manual reloads. The install fetches each shell file on its own, up to 3 tries (with `addAll`, one failed request on an unstable line failed the whole install). Versioned files (`?v=` in the URL) and `fonts/` are cache-first (a new version is a new URL), so a launch needs no network once cached. The other app files (page, `curation.json`, manifest) are revalidated with the server, but a file already cached is served after 2 s (`SLOW`) on a slow link while the network refreshes the cache in the background.
- Speed on poor connections and low-end phones (Pierre, 2026-11-01; measured with `node tools/perf.js`, network × CPU profiles, and `node tools/perf.js field`, the field link below):
  - **Load order in tiers** (Pierre, 2026-11-02). A real RA's first visit from the IMR field station (HAR, Chrome) was served from Fastly's Manila POP (latency ~0.4 s, fine) but at ~86 kbit/s: at 0.5 s the page asked for everything at once (fonts, data.json, the 12 scripts, the Lab stylesheet and hub), each file got a sliver of the line and all came together at 20-25 s; then the service worker's install fetched the rest of the shell (Lab prototypes, fonts...) while the first quiz photo (960 px, 62 KB) came at 47 s. Now the files come one tier after the other, so what the player waits for never shares the line with the rest: **1 Home** (`app.css`, `proto/lab.css`, which also holds the layout of Home, My progress and the games' side columns (`.pgame`, `data-page=lab`), `home.css`, the main font, `core.js`, `app.js`, `sync.js`, `home-art.js`, `home.js`, `tour.js`, `data.json`, `curation.json`), **2 the photo quiz** (`model.js`, `quiz.js`, `learn.js`, which the quiz uses for its look-alike pairs and mix-up montages, `progress.js`, 13 KB, which each answer updates (achievements) and which opens My progress at once (Codex review #361: answers given before it lost their achievement bookkeeping, and a sign-in from the tour reached its record before it existed: the sign-in now waits for tier 2), with `forms.json`, `quality.json` and `picks.json`, which the draw and the photo slots use: the data is rebuilt with them, then the achievements are counted and the sheet's photo statistics asked for), **3 the photos of the next quiz questions** (planned at once, see Quiz below), **4 the sheet's reads** (sync, anonymous answers, leaderboard, achievement shares), **5 the rest** (`flag.js`, `proto/lab.js` with the Lab prototypes), then the service worker is registered: its install caches every other shell file (italic and condensed fonts, Lab...) for the next visit, which stays instant. Home's doors need data.json (the photo band), so Home waits for it; Home's own photos are lazy thumbnails. The tiers are listed in `index.html` (tier 1 as `<link rel=preload as=script data-tier=1>`, later ones as bare `<link data-tier=N href>`, which fetch nothing until the loader turns them into preloads); `loadTier(N)` in the inline loader starts tiers 2..N at once and resolves once their scripts have run, in order; `need(N)` in `app.js` adds each tier's set-up (`SETUP`) and `HAVE` is the last tier in. A page opened before its files arrived (`pageTier`: Home 1; quiz, duels, Learn pages, My progress, leaderboard and achievements 2; Tools and Coral Finder 5) shows the loading bar and asks for its tier at once, ahead of the queue (`route()`); a link straight to a page asks for its tier at start-up, alongside Home's files. `window.APP_READY` is set once tier 2 is in (Home, the quiz and the Learn pages work). Field link, phone, first visit (`tools/perf.js field`, one run each, so a few seconds of noise), before → after: Home shown 37.3 → 20.9 s (387 → 213 KB before it), first quiz photo when the player goes straight to the quiz from Home 69 → 38 s from the start, Next → photo for questions 2-5 22/24/7/25 → 10/12/0/0 s, My progress 37 → 28 s from the start (tap on Home), first quiz photo after 30 s on Home 29 → 6 s after the tap. On a desktop, Home also comes at 21 s instead of 37 s, and with Saver taking the 480 px file whatever the box the first quiz photo comes +18.6 s after the tap instead of +37.8 s, Next → photo for questions 2-5 4/5/0/9 s instead of 35/21/22/27 s. A photo-quiz question that changes what comes next (an exam question, a slipped-in duel, an "Again", cards) is answered before anything is planned past it (Codex review #361: an exam planned behind an unanswered exam broke its spacing).
  - Start-up never waits for `curation.json` when a kept copy exists (`CUR_KEPT`); `curRefresh` reads it right after, and a change applies at the next screen.
  - Quiz: the next questions are chosen ahead, up to 3 in the photo quiz (`AHEAD`; one in the Duel tab), and their photos fetched meanwhile, so Next shows one at once (`planNext`, `NEXTQ` holding the next ones in `.next`, each keyed on the answers count it is for and the genera in play; Pierre, 2026-11-02: a fluent RA answers in ~8 s, less than one question's photos take at 86 kbit/s, and 95% of the answers are in the photo quiz). The queue is topped up when a question shows and after each answer. Planning ahead keeps the rules of the draw: a question with cards, an exam question, a duel slipped in or an "Again" ends the queue (nothing is chosen past it before it is played), and a wrong answer drops the queue, putting the planner's own state back (`dropPlans`: genus asked last, duel and "Again" spacing), so the "Again" still comes one question later. After a right answer the questions already chosen stay: their weights lag up to 2 answers, and a new card, exam question or duel can come up to 2 questions later than without planning ahead. The photos come in order of need, two at a time, question after question (cards of the genera met, then the photos shown small then full size, then hint and other views; `pump`, with `fetch()`, which unlike `new Image()` does not hold the page's load event): all at once they shared a slow line and the first photo came later than without preloading. The first questions are planned as soon as tier 2 is in.
  - Start-up on an unstable line: the JSON files are fetched again on failure, up to 3 tries (`getR`); each tier's scripts are preloaded (downloaded in parallel) and run in order by an inline loader in `index.html` (its own CSP hash), each failed one tried again up to 3 times; `window.BOOT` resolves once tier 1 has run, and app.js waits for it before the first page (`domReady`). A failed stylesheet is tried again the same way, and so are the Lab prototypes (`labLoad`). data.json is preloaded too (`as=fetch crossorigin`, same URL as the fetch, so it downloads alongside the scripts). Under "Loading…" a bar moves one step per script run and one for data.json (`bootTick`; it counts tier 1, or the tiers the first page needs: `bootMax`), and after 6 s a line says only the first visit is this slow (beginner RA review, 2026-11-02: 5-8 s of a bare "Loading…" at 400 kbps looked stuck). If data.json still fails, the page offers Try again. A first version reloaded the whole page on a failed file: on a line failing 1 request in 5, every reload failed again. Before, one failed request among ~10 start-up files left the app on Loading for good (`tools/perf.js`, 1 request in 5 failing, no service worker yet).
  - Pages: leaving a page drops its photos still loading (`route()`), so a slow line goes to the new page.
  - Photo sizes (Pierre, 2026-11-01): each photo exists in 1600, 960 (`-m`), 480 (`-s`) and 240 px (`-t`). A big photo (quiz, Look-alikes, sheet cover, lab tools) gets the smallest file that covers its box at the screen's density counted up to 2x (`fit`); the quiz guesses the box from the last question with as many photos (`QBOX`, so the preload fetches the right file), and a box bigger than guessed loads the bigger file (`upsizeImg`, `upsize`, never smaller). Cards and strips use `srcset` with the 480, 960 and 1600 px files (card `sizes` measured per S/M/L setting). Thumbnails (home band, progress tiles, look-alike pairs, tips) use `thumb()`: 240 or 480 px by drawn width and density (a home tile on a phone is ~60 px: 240 px, ~10 KB, instead of 480 px, ~30 KB). The home ReefCloud art has a 760 px version for phones. Leaving a page drops `srcset` with `src`, or the download goes on. The enlarged view loads the 1600 px file over the 480 px one. A photo not downloaded yet (`r: 1`: a candidate just added, and all of Millepora's game photos, `DATA.x.gen`) loads from iNaturalist with two files only (`img()`): `medium` (500 px) for the 480 px size, `large` (1024 px) for 960 and 1600 px; `resized()`, `upsizeImg` and the preload (`pfUrls`) leave it alone. A quiz photo carries its name in `data-f` (`quiz.js` `question`), so the failed-photo report (`ev('photo')`, admin "Photos not loaded") and the tests (`net.smoke.js`, `profiles.smoke.js`, `tools/perf.js`) name an iNaturalist photo by its `f`, not by its URL.
  - Photo quality setting (`imr-photo-q`): Auto (default), Saver, Full. Saver takes the 480 px file for a big photo whatever its box (shown whole at its own size on a bigger desktop box, LOWRES; field link: at 1x a desktop quiz box still took the 960 px file, two per question), drops the 1600 px file from `srcset`, gives thumbnails their 240 px file and Home's ReefCloud art its 760 px one (field link: Home's photos on a desktop came to ~600 KB), and the enlarged view starts at 960 px (1600 on a click). Auto is Saver when the browser reports the data saver or a 2g/3g connection (Network Information API, Chrome on Android), or, once the app has measured the line itself, when it is under 500 kbit/s (Pierre: 480 px photos on a 1080p or 4K desktop are a real loss; the browser's estimate only counts before a measure; `linkMeasure`, `LINK`: the bytes the page got from the network over the time spent receiving them, Resource Timing, overlapping downloads counted once, cached files not at all, once 40 KB are in; kept in `imr-link` for a launch served from the cache). Field HAR, 2026-11-02: at ~86 kbit/s Chrome's estimate did not flag the link, so Auto loaded the 960 px quiz photo (62 KB, 19 s); Safari and Firefox have no Network Information API. Saver never moves a shown photo to a bigger file (`upsizeImg`); only the enlarged view does, on a tap. Full always loads 1600 px for big photos.
  - Each game photo shows its 480 px version (`data-lo`, also the blurred backdrop) as the image's background until the bigger one is in.
  - A failing photo is retried twice (after 1 s, then 4 s), then replaced by its 480 px version. If that fails too, the question offers another one, and nothing is counted.
  - The leaderboard and achievement shares are kept on the device (`imr-board-cache`, `imr-achs-cache`): drawn at once, then refreshed. They are fetched with tier 4, after the quiz and its next photos.
  - Fonts are served from `fonts/` (latin subset, SIL OFL), not Google Fonts.
- `privacy.html`: the privacy notice (static, no script, own CSP), linked from the ? help of every page and from About and credits (`#about`); also the privacy policy link of the Google Cloud project behind the sync script's self-update. Keep it true when the data stored changes (new Sheet column, new external host).
- Link preview (Pierre, 2026-11-01): `index.html` carries Open Graph / Twitter meta tags pointing at `og.jpg` (1200 × 630, six of Pierre's own photos + the app name), made by `node tools/og/make_og.js` from `tools/og/og.html`. Absolute URLs (crawlers need them); WhatsApp caches a preview per URL, so an old share keeps its old card.
- Everything runs in the browser. The only backend is a Google Apps Script web app that stores RA progress in a Google Sheet.

## Security model

What is public, what protects what (code review, 2026-11-01).
- **Everything in the repo is public**, including the admin page code and the sync URL. The admin password only unlocks the token stored in that browser; it protects nothing on its own.
- **The GitHub token is the real key**: fine-grained, this repo only, Contents read/write, 90-day expiry. Kept encrypted in `localStorage` (`imr-admin-vault`); the unlocked token lives in `sessionStorage` only. `ppericard.github.io` is shared by every Pages site of the account, so never add third-party scripts: the CSP (`<meta http-equiv="Content-Security-Policy">` in `index.html` and `admin.html`) allows scripts from this site only, inline scripts by hash (`tests/csp.test.js` fails if a hash is stale). Add a host to `img-src` / `connect-src` there when a new external source is needed. The R2 bucket (`https://pub-934250f83b884a4f890497f2027ce251.r2.dev`) is in `img-src` (the photos) and `connect-src` (any `fetch()` of a photo; the service worker's own requests follow no page CSP).
- **Templates**: every data string goes through `esc()` (escapes `& < > " '`); links from data go through `safeUrl()` (https only).
- **Sync sheet**: anyone can call the Apps Script URL. A name + 4-digit code only prevents accidental overwrites; v6 throttles wrong codes, never writes a user string as a formula, and keeps anonymous ids unguessable (secret salt). RA data is low-sensitivity (first names and quiz answers).
- **GitHub Action** (`approved-photos.yml`, `contents: write`): downloads photos only from iNaturalist hosts (`tools/fetch_approved.py` `HOSTS`).
- **Photos to R2** (`photos-r2.yml` and the last step of `approved-photos.yml` (its `r2` job), `tools/r2_sync.sh`; Pierre, 2026-11-03; both in the concurrency group `photos-r2`, so one writer at a time): `img/` mirrored to the Cloudflare R2 bucket (public address `https://pub-934250f83b884a4f890497f2027ce251.r2.dev`, CORS for the site and localhost) with rclone and an R2 API token limited to that bucket (Object Read & Write), from the repo's secrets; files compared by checksum, a file removed from `img/` removed from the bucket. Step 1 of "Photos out of the repo" (ROADMAP). Step 2: the app and the admin read the photos from there, the site's `img/` as the fallback ("Photos").

## Players' reports (2026-11-01)

In every game (Quiz, Custom quiz, Look-alike duels, Memory, Reveal), once the answer is out, the feedback shows a discreet "⚑ Report a problem" (`repBtn()` in `sync.js`; Lab games call it if present). It opens a small dialog (`reportDialog()`): Wrong answer (with a "Right genus, if you know" field, suggestions from the 39 genera), Several corals, Bad photo, Other, an optional note, and "Your name" when the player is not signed in to the sync. A report carries the photos of the question (one observation), the expected genus, the answer given and the game. Reports queue in `localStorage` `imr-reports` and are sent by `sendReports()` (on send, start-up and when back online) to `Code.gs` v7; an older script leaves them queued. Admin To do (views All and Reports; script v8) lists them first ("Reports and feedback", `renderTriage` `repCard`), with the reporter's name (a `?` after it = not verified by a sync code), each photo with every tool of its genus page, and ✓ Done per report (`seen['rep:id']`).
