# Architecture

How the app is put together. Rules and workflow are in [`../AGENTS.md`](../AGENTS.md); deferred ideas in [`ROADMAP.md`](ROADMAP.md).

## Overview

```
data.json (genus data + photo lists) ──┐
forms.json / quality.json / picks.json ├─> app.js (applyCuration + applySlots from core.js, applyForms) ─> pages
curation.json (Pierre's choices) ──────┘                                    │
                                                                            └─> progress in localStorage ─> Apps Script ─> Google Sheet
admin.html ──(GitHub Contents API, Pierre's token)──> curation.json on main ──> GitHub Action fetches approved photos
```

- Static site served by GitHub Pages from `main` via `pages.yml` (Actions source; migration and recovery in [PAGES.md](PAGES.md)). No framework, no bundler, no npm.
- A service worker (`sw.js`) caches the app shell for offline use (versioned cache `V`, replaced on each deploy) and photos as they are viewed, in a separate cache `imr-photos-v1` that deploys never delete (capped at 2,500 entries, only good replies kept). `curation.json` is part of the shell, so the first offline launch after a deploy still has Pierre's choices; the app also keeps the last curation it read in `localStorage` (`imr-curation-last`) as a fallback. **New versions reach players without a manual reload** (Pierre, 2026-11-02): each deploy changes `sw.js` (`V`), which the browser checks at each launch and the app re-checks when it comes back into view (5 min apart) and every 30 min (`swCheck`); the new worker installs in the background and takes over (`skipWaiting`, `clients.claim`), and the page then reloads itself when it next comes into view or at the next page change (`UPDATED`, `route()`), never in the middle of a page. The admin page does the same (`admin.js`, every click is already in the draft; not while the draft could not be saved). Before, a slow line served the old cached page after 2 s, so it took one or two manual reloads. The install fetches each shell file on its own, up to 3 tries (with `addAll`, one failed request on an unstable line failed the whole install). Versioned files (`?v=` in the URL) and `fonts/` are cache-first (a new version is a new URL), so a launch needs no network once cached. The other app files (page, `curation.json`, manifest) are revalidated with the server, but a file already cached is served after 2 s (`SLOW`) on a slow link while the network refreshes the cache in the background.
- Speed on poor connections and low-end phones (Pierre, 2026-11-01; measured with `node tools/perf.js`, network × CPU profiles, and `node tools/perf.js field`, the field link below):
  - **Load order in tiers** (Pierre, 2026-11-02). A real RA's first visit from the IMR field station (HAR, Chrome) was served from Fastly's Manila POP (latency ~0.4 s, fine) but at ~86 kbit/s: at 0.5 s the page asked for everything at once (fonts, data.json, the 12 scripts, the Lab stylesheet and hub), each file got a sliver of the line and all came together at 20-25 s; then the service worker's install fetched the rest of the shell (Lab prototypes, fonts...) while the first quiz photo (960 px, 62 KB) came at 47 s. Now the files come one tier after the other, so what the player waits for never shares the line with the rest: **1 Home** (`app.css`, `proto/lab.css`, which also holds the layout of Home, My progress and the games' side columns (`.pgame`, `data-page=lab`), `home.css`, the main font, `core.js`, `app.js`, `sync.js`, `home-art.js`, `home.js`, `tour.js`, `data.json`, `curation.json`), **2 the photo quiz** (`model.js`, `quiz.js`, `learn.js`, which the quiz uses for its look-alike pairs and mix-up montages, `progress.js`, 13 KB, which each answer updates (achievements) and which opens My progress at once (Codex review #361: answers given before it lost their achievement bookkeeping, and a sign-in from the tour reached its record before it existed: the sign-in now waits for tier 2), with `forms.json`, `quality.json` and `picks.json`, which the draw and the photo slots use: the data is rebuilt with them, then the achievements are counted and the sheet's photo statistics asked for), **3 the photos of the next quiz questions** (planned at once, see Quiz below), **4 the sheet's reads** (sync, anonymous answers, leaderboard, achievement shares), **5 the rest** (`flag.js`, `proto/lab.js` with the Lab prototypes), then the service worker is registered: its install caches every other shell file (italic and condensed fonts, Lab...) for the next visit, which stays instant. Home's doors need data.json (the photo band), so Home waits for it; Home's own photos are lazy thumbnails. The tiers are listed in `index.html` (tier 1 as `<link rel=preload as=script data-tier=1>`, later ones as bare `<link data-tier=N href>`, which fetch nothing until the loader turns them into preloads); `loadTier(N)` in the inline loader starts tiers 2..N at once and resolves once their scripts have run, in order; `need(N)` in `app.js` adds each tier's set-up (`SETUP`) and `HAVE` is the last tier in. A page opened before its files arrived (`pageTier`: Home 1; quiz, duels, Learn pages, My progress, leaderboard and achievements 2; Tools and Coral Finder 5) shows the loading bar and asks for its tier at once, ahead of the queue (`route()`); a link straight to a page asks for its tier at start-up, alongside Home's files. `window.APP_READY` is set once tier 2 is in (Home, the quiz and the Learn pages work). Field link, phone, first visit (`tools/perf.js field`, one run each, so a few seconds of noise), before → after: Home shown 37.3 → 20.9 s (387 → 213 KB before it), first quiz photo when the player goes straight to the quiz from Home 69 → 38 s from the start, Next → photo for questions 2-5 22/24/7/25 → 10/12/0/0 s, My progress 37 → 28 s from the start (tap on Home), first quiz photo after 30 s on Home 29 → 6 s after the tap. On a desktop, Home also comes at 21 s instead of 37 s, and with Saver taking the 480 px file whatever the box the first quiz photo comes +18.6 s after the tap instead of +37.8 s, Next → photo for questions 2-5 4/5/0/9 s instead of 35/21/22/27 s. A photo-quiz question that changes what comes next (an exam question, a slipped-in duel, an "Again", cards) is answered before anything is planned past it (Codex review #361: an exam planned behind an unanswered exam broke its spacing).
  - Start-up never waits for `curation.json` when a kept copy exists (`CUR_KEPT`); `curRefresh` reads it right after, and a change applies at the next screen.
  - Quiz: the next questions are chosen ahead, up to 3 in the photo quiz (`AHEAD`; one in the Duel tab), and their photos fetched meanwhile, so Next shows one at once (`planNext`, `NEXTQ` holding the next ones in `.next`, each keyed on the answers count it is for and the genera in play; Pierre, 2026-11-02: a fluent RA answers in ~8 s, less than one question's photos take at 86 kbit/s, and 95% of the answers are in the photo quiz). The queue is topped up when a question shows and after each answer. Planning ahead keeps the rules of the draw: a question with cards, an exam question, a duel slipped in or an "Again" ends the queue (nothing is chosen past it before it is played), and a wrong answer drops the queue, putting the planner's own state back (`dropPlans`: genus asked last, duel and "Again" spacing), so the "Again" still comes one question later. After a right answer the questions already chosen stay: their weights lag up to 2 answers, and a new card, exam question or duel can come up to 2 questions later than without planning ahead. The photos come in order of need, two at a time, question after question (cards of the genera met, then the photos shown small then full size, then hint and other views; `pump`, with `fetch()`, which unlike `new Image()` does not hold the page's load event): all at once they shared a slow line and the first photo came later than without preloading. The first questions are planned as soon as tier 2 is in.
  - Start-up on an unstable line: the JSON files are fetched again on failure, up to 3 tries (`getR`); each tier's scripts are preloaded (downloaded in parallel) and run in order by an inline loader in `index.html` (its own CSP hash), each failed one tried again up to 3 times; `window.BOOT` resolves once tier 1 has run, and app.js waits for it before the first page (`domReady`). A failed stylesheet is tried again the same way, and so are the Lab prototypes (`labLoad`). data.json is preloaded too (`as=fetch crossorigin`, same URL as the fetch, so it downloads alongside the scripts). Under "Loading…" a bar moves one step per script run and one for data.json (`bootTick`; it counts tier 1, or the tiers the first page needs: `bootMax`), and after 6 s a line says only the first visit is this slow (beginner RA review, 2026-11-02: 5-8 s of a bare "Loading…" at 400 kbps looked stuck). If data.json still fails, the page offers Try again. A first version reloaded the whole page on a failed file: on a line failing 1 request in 5, every reload failed again. Before, one failed request among ~10 start-up files left the app on Loading for good (`tools/perf.js`, 1 request in 5 failing, no service worker yet).
  - Pages: leaving a page drops its photos still loading (`route()`), so a slow line goes to the new page.
  - Photo sizes (Pierre, 2026-11-01): each photo exists in 1600, 960 (`-m`), 480 (`-s`) and 240 px (`-t`). A big photo (quiz, Look-alikes, sheet cover, lab tools) gets the smallest file that covers its box at the screen's density counted up to 2x (`fit`); the quiz guesses the box from the last question with as many photos (`QBOX`, so the preload fetches the right file), and a box bigger than guessed loads the bigger file (`upsizeImg`, `upsize`, never smaller). Cards and strips use `srcset` with the 480, 960 and 1600 px files (card `sizes` measured per S/M/L setting). Thumbnails (home band, progress tiles, look-alike pairs, tips) use `thumb()`: 240 or 480 px by drawn width and density (a home tile on a phone is ~60 px: 240 px, ~10 KB, instead of 480 px, ~30 KB). The home ReefCloud art has a 760 px version for phones. Leaving a page drops `srcset` with `src`, or the download goes on. The enlarged view loads the 1600 px file over the 480 px one.
  - Photo quality setting (`imr-photo-q`): Auto (default), Saver, Full. Saver takes the 480 px file for a big photo whatever its box (shown whole at its own size on a bigger desktop box, LOWRES; field link: at 1x a desktop quiz box still took the 960 px file, two per question), drops the 1600 px file from `srcset`, gives thumbnails their 240 px file and Home's ReefCloud art its 760 px one (field link: Home's photos on a desktop came to ~600 KB), and the enlarged view starts at 960 px (1600 on a click). Auto is Saver when the browser reports the data saver or a 2g/3g connection (Network Information API, Chrome on Android), or, once the app has measured the line itself, when it is under 500 kbit/s (Pierre: 480 px photos on a 1080p or 4K desktop are a real loss; the browser's estimate only counts before a measure; `linkMeasure`, `LINK`: the bytes the page got from the network over the time spent receiving them, Resource Timing, overlapping downloads counted once, cached files not at all, once 40 KB are in; kept in `imr-link` for a launch served from the cache). Field HAR, 2026-11-02: at ~86 kbit/s Chrome's estimate did not flag the link, so Auto loaded the 960 px quiz photo (62 KB, 19 s); Safari and Firefox have no Network Information API. Saver never moves a shown photo to a bigger file (`upsizeImg`); only the enlarged view does, on a tap. Full always loads 1600 px for big photos.
  - Each game photo shows its 480 px version (`data-lo`, also the blurred backdrop) as the image's background until the bigger one is in.
  - A failing photo is retried twice (after 1 s, then 4 s), then replaced by its 480 px version. If that fails too, the question offers another one, and nothing is counted.
  - The leaderboard and achievement shares are kept on the device (`imr-board-cache`, `imr-achs-cache`): drawn at once, then refreshed. They are fetched with tier 4, after the quiz and its next photos.
  - Fonts are served from `fonts/` (latin subset, SIL OFL), not Google Fonts.
- `privacy.html`: the privacy notice (static, no script, own CSP), linked from the footer; also the privacy policy link of the Google Cloud project behind the sync script's self-update. Keep it true when the data stored changes (new Sheet column, new external host).
- Link preview (Pierre, 2026-11-01): `index.html` carries Open Graph / Twitter meta tags pointing at `og.jpg` (1200 × 630, six of Pierre's own photos + the app name), made by `node tools/og/make_og.js` from `tools/og/og.html`. Absolute URLs (crawlers need them); WhatsApp caches a preview per URL, so an old share keeps its old card.
- Everything runs in the browser. The only backend is a Google Apps Script web app that stores RA progress in a Google Sheet.

### Learning model (`model.js`, split out of `app.js` 2026-11-02)
- Per-genus state in `localStorage` `imr-coral-progress` (`P[genus]`: `ok`, `ko`, `h` recent results string (last 10), `pg` progress (moving average, `core.js` `PROG`; `L`, BKT knowledge, in progress saved before 2026-11-02), `th` ability, `ps` photos seen `{f: [seen, right]}`, `ro` recent colonies, `cor`/`du` milestones).
- **Learning model**: research and choices are in [LEARNING.md](LEARNING.md) (2026-11-02: three player paths without coded tracks; progressive opening of genera `OPEN`/`genusDiff`/`shaky`, volatility in `abilityStep` `ELO.vr`/`vg`, pooled traps for experts `pooledConf`, met genera first as easy wrong choices; the progress bar as a moving average weighed by what each answer proves, `PROG`, `pgWeight`, replacing BKT; simulated by `tests/profiles.smoke.js`, learning outcomes over many seeds by `tools/learnsim.js`). The paragraphs below describe the code.
- **Learned** = the **silent mastery exam** passed (`s.mx`; Pierre, 2026-11-01: "an ultimate test from 95% to 100%"; the former two milestones, right once with the corallites in view and once in a duel, were dropped as easy and arbitrary). The progress `s.pg` (a moving average of the answers weighed by what each proves: `core.js` `PROG`, `pgStep`, `pgOf`; `model.js` `pgWeight`, `pgObs`, `knownP(n)`; BKT until 2026-11-02) fills a genus up to 95%; once `knownP` ≥ `PROG.M` = 0.8 (`examOn`), `EXAM.n` = 5 questions on it are slipped unannounced into the photo quiz (`quizPhoto` → `examSet`), at least `EXAM.gap` = 8 answers apart (`examReady`, counted in answers, never time; `weight()` raises a genus ready for its next exam question to 3 and holds it back in between): one photo alone, never answered right before (else the least seen), the hardest of its view, the views taking turns (`s.ex = {k, v, at}`), 3 look-alike traps. All right: `s.mx = 1` and a pop-up; mastery is kept while the genus stays known (two misses before it is back up, for the genus shown or the one answered, take it away and bring the exam back). Exam photos are never-shown ones first. The exam's count is shown nowhere (Pierre: only the genus's %, which creeps up from 95% and falls back on a miss, keeps the mystery). Any miss on the genus (exam or not) and any time it is given as the answer for another genus drops `s.ex`; it starts again when `pg` is back at the entry. `mergeProgress` takes `mx` and `ex` from the device that played, like `pg`. `tests/draw.smoke.js` plays an exam through the real quiz. A right answer weighs (1 − 1/k) / (3/4) with k plausible choices, halved when none of its look-alikes is among the choices; a miss weighs the Elo chance of a right answer over the ~80% the photos aim for, at most 1 (`pgMissW`: in full at the player's level, less on a harder photo); a learned genus survives one miss (`mxKept`) and loses its mastery on a second one before it is back up. Progress saved before `pg` is recomputed from its last 10 results (`pgOf`, the same in the sheet's `pctOf_`, v22). **Review** = 2+ misses in the last 5 results. **No time criteria anywhere** (rule).
- A wrong answer is a failed observation for the genus shown **and** the genus given (rule).
- **Progress scale**: `genScore` (`core.js` `scoreOf`) = 0.95 × min(1, `pg` / `PROG.M`), + 1% per exam question passed, 1 once mastered; `lvStep` = 6 steps (0 not seen, 1-4 quarters of `genScore`, 5 learned) coloured by the palette's learning-level ramp; tiles on My progress (Photos / Slate / Groups views) show a mini ring + %; review = red border and "!" (dashed in colour-blind mode). `progPct` drives the header ring.
- **Which genus next**: `weight()` favours unseen (10), review and unsure genera, learned 0.25, and holds back the last 4 genera asked. Bonus genera weigh at most `BONUS_W` = 4 (as a genus being learned, even when new or to review), and all of them together at most `BONUS_SHARE` = 15% of the draw (`weighted()` scales them down; Pierre, 2026-11-01, after a burst of bonus questions right after unlocking some: simulated 34% before, 15% after).
- **Continuous difficulty** (Elo as in Pelánek 2016; PRs #197, #200): per-genus ability `P[n].th` on the photo-difficulty scale, updated by `abilityStep()` with P(right) = g + (1-g)·sigmoid(ability − difficulty), g = 1/choices, K shrinking with answers but ≥ 0.25 (`ELO`). **Global level** (Pierre, 2026-11-01: strong beta testers must not wait ~100 questions for traps): the same Elo step runs over every answer into the pseudo-genus `P['~level']` (`LEVEL` in `core.js`; ok, ko, th like a genus, so it syncs and merges like one, and appears in the sheet's per-genus abilities under that key). A genus never answered starts from `playerStart(P, n)` (`core.js`): 0.8 × global ability × M/(M+10) (M = its answers), clamped to [−0.5, 1.5] (`START`); progress saved before falls back on the answer-weighted mean of the genera's abilities, and the record is made at the next answer from that history (`levelSeed()`: all answers so far, that mean), so an existing player's earlier answers keep counting. Taken once: the first answer saves the genus's own `th`. Simulated (real `photoSet`/`distractors`, all right): traps over the first 25 questions 1.9 on average instead of 0.1, 2.8 over questions 26-50 instead of 0.5; a player at 50% stays at 0 traps, starting new genera at −0.5. Progress (`pg`) is not carried over: each genus is still proven by its own answers. `photoSet()` draws photos weighted around the target `ability − 1.0` (~80% right in a 4-choice question, `PICKD`), with a bonus for never-seen photos (IMR and Pierre's first), photos answered right twice down-weighted, the last colonies held back and ≥ 3 colonies in rotation (`VARIETY`). **Answer choices** (Pierre, 2026-11-01) follow the same ability: `trapsFor(t)` = how many of the 3 wrong choices are look-alikes of the target (`look` both ways), 0 on a genus's first question (ability 0), then +1 per 0.18 (`TRAP`), randomly rounded in between, all 3 from 0.54: one look-alike after the first right answer, all three after about 5, because they are how genera are learned (Pierre, 2026-11-01). While traps are 0-1 the other wrong choices are genera sharing no IMR growth form with the target (`imrFormsOf`), other lecture groups first and each in a different growth form (so the answer is not the odd one out); from 2 traps the last choice is family first, then any genus (the old rule). With 0-1 trap, Elo (and the progress weight) use g = 1/k with k = target + plausible wrong choices (`plausibleK()`: look-alikes or a shared growth form, min 2), and the answer log records the mode as `quiz|kN` so the sheet's `stats_` (Code.gs v9) and `eloOf()` (`core.js`) rate the photo with the same guess rate; an older sheet script treats it as 4 choices. **Confusion scores** (Pierre, 2026-11-01: real mix-ups are more relevant than the declared look-alikes alone, which only initialise them): the look-alike traps are the genera with the highest `confOf(t, n)` = `confScore()` (`core.js`): mixed up / offered together for the pair, pooled over every RA (`?stats=1` `conf`, Code.gs v10), starting from a prior worth `CONF.W` = 8 offers (declared look-alike 0.3, same family 0.12, shared IMR growth form 0.08, other 0.03). A pair is a trap (`confusable`) from `CONF.TRAP` = 0.2, so a declared pair nobody confuses fades and an undeclared one players do confuse becomes a trap; scores are shuffled ±20% so close pairs all get tried. `plausibleK()` counts confusable choices. Every answer logs the choices offered (`ch`, Code.gs v10 `Choices` column); without v10 deployed `conf` is empty and the priors alone apply (the old behaviour). **Personal path** (Pierre, 2026-11-01): that pooled score is then the prior for the player's own record on the pair, `pairConf(P, a, b)` (`core.js`) = [offered together, mixed up] in both directions from `P[g].off` (each wrong choice shown beside `g`, counted in `answer()` since 2026-11-01) and `P[g].conf` (genus answered instead), again worth `CONF.W` offers, so the player's weight is offers / (offers + 8). A pair a player keeps mixing up becomes their trap even if others don't confuse it; one they now tell apart sinks back. Duels weigh pairs ×3 when the player mixed them up and still confuses them, ×2 when `confusable` or a classic, else ×1. ## Security model

What is public, what protects what (code review, 2026-11-01).
- **Everything in the repo is public**, including the admin page code and the sync URL. The admin password only unlocks the token stored in that browser; it protects nothing on its own.
- **The GitHub token is the real key**: fine-grained, this repo only, Contents read/write, 90-day expiry. Kept encrypted in `localStorage` (`imr-admin-vault`); the unlocked token lives in `sessionStorage` only. `ppericard.github.io` is shared by every Pages site of the account, so never add third-party scripts: the CSP (`<meta http-equiv="Content-Security-Policy">` in `index.html` and `admin.html`) allows scripts from this site only, inline scripts by hash (`tests/csp.test.js` fails if a hash is stale). Add a host to `img-src` / `connect-src` there when a new external source is needed.
- **Templates**: every data string goes through `esc()` (escapes `& < > " '`); links from data go through `safeUrl()` (https only).
- **Sync sheet**: anyone can call the Apps Script URL. A name + 4-digit code only prevents accidental overwrites; v6 throttles wrong codes, never writes a user string as a formula, and keeps anonymous ids unguessable (secret salt). RA data is low-sensitivity (first names and quiz answers).
- **GitHub Action** (`approved-photos.yml`, `contents: write`): downloads photos only from iNaturalist hosts (`tools/fetch_approved.py` `HOSTS`).

Many were one-off steps of the original build and read a scratchpad that no longer exists (`make_site.py`, `build_photos.py`, `apply_levels.py`, `build_lecture_more.py`, `coral_finder_book/*`): they now live in `tools/archive/` (kept for reference, cannot be re-run); edit `data.json` directly instead, and write it with `tools/datajson.py`.

Still useful / re-runnable:
| Script | Purpose |
|---|---|
| `photos.py` | The four photo sizes (`SIZES`, `save()`, `remove()`); fills missing smaller files, `--check` (CI and the photo Action). |
| `fetch_approved.py`, `fetch_local.py` | Candidate download/refill (run by the GitHub Action; `fetch_local.py <Genus…>` to limit). |
| `photo_quality.py` | Automatic quality → `quality.json`. |
| `find_dups.py` | Near-duplicates → `dups.json` (re-run after adding photos). |
| `tag_origin.py` | `loc` tag (dauin/ph/world) on iNat photos. |
| `judging_manifest.py`, `judging_import.py`, `judging_cand.py` | Outside photo-judging agent package (`judging/`); `--check` validates. |
| `apply_id_tips.py` | `tools/id_tips.txt` → `gen[g].qt`. |
| `apply_imr_forms.py` | IMR growth form definitions into `forms.json`. |

## Run and deploy

- Run: `python3 -m http.server 8000` at the repo root, open <http://localhost:8000> (`admin.html` for the back-office; without a token use `admin.html?demo`, made-up data, or `admin.html?readonly`, the real public curation). Sync and photo Elo talk to the live Apps Script even locally.
- Deploy: `.github/workflows/pages.yml` publishes current `main` as a static artifact, with one `pages` concurrency group and `cancel-in-progress: true`. Settings > Pages must use **GitHub Actions**; the workflow fails early while the legacy branch source is selected. Migration, incident evidence and CLI recovery: [PAGES.md](PAGES.md).
- Pierre's Publish pushes `curation.json` to `main`, triggering both Deploy Pages and Candidate photos. The latter commits `data.json`/`img` using `GITHUB_TOKEN`; its completion triggers Deploy Pages again so bot changes are published too.
- The service worker serves the cached shell, so bump `?v=` numbers and `sw.js` `V` (see AGENTS.md) for shell changes. `curation.json` is fetched with `no-cache` (from the kept copy first at start-up, see above).
- A completed Actions run can leave a stale Pages backend lock. Cancel the blocking **Pages deployment** as well as any stuck Actions run, then dispatch `pages.yml` on `main`; see [PAGES.md](PAGES.md#manual-recovery). Repeatedly rerunning the blocking legacy SHA is not the fix.

## Players' reports (2026-11-01)

In every game (Photo → genus, Look-alike duels, Memory, Reveal), once the answer is out, the feedback shows a discreet "⚑ Report a problem" (`repBtn()` in `sync.js`; Lab games call it if present). It opens a small dialog (`reportDialog()`): Wrong answer (with a "Right genus, if you know" field, suggestions from the 39 genera), Several corals, Bad photo, Other, an optional note, and "Your name" when the player is not signed in to the sync. A report carries the photos of the question (one observation), the expected genus, the answer given and the game. Reports queue in `localStorage` `imr-reports` and are sent by `sendReports()` (on send, start-up and when back online) to `Code.gs` v7; an older script leaves them queued. Admin Triage (script v8) lists them first ("Reported by players", `renderTriage` `repCard`), with the reporter's name (a `?` after it = not verified by a sync code), each photo with every tool of its genus page, and ✓ Done per report (`seen['rep:id']`). Since v8 the same dialog also opens from "⚑ Report" in the caption of any enlarged photo (lightbox, not while a game hides the genus; reasons Wrong genus, Several corals, Bad photo, Other), "⚑ Report a problem with this sheet" at the bottom of a genus sheet (Wrong information, Bad photo, Other) and "Send feedback" in the footer of every page (Wrong information, Bug, Suggestion, Other); `REP_WHY[kind]`, and every report carries the page it came from (`w`, sheet column `Where`). Nothing is ever changed automatically from a report. Pierre's own ⚑ flag (`flag.js`) is separate and stays admin-only.
