A player's report can carry a screenshot or photo (Pierre, 2026-11-21 05:48, Q446: «Environ 800 pixels en JPEG léger … le script la range directement dans la feuille, dans un onglet à part … je la lis quand il traite le rapport, puis on l'efface»). `logReports_` takes an optional `img` (`{t: 'image/jpeg', d: base64}`) on a report, which the app reduced on the phone (about 800 px, JPEG, no EXIF), and keeps it in the new `Report images` tab, one row a report: Id (the report's), Time, Player (the reporter's anonymous id, empty without a name), Type, Bytes, then the base64 text in chunks of 45,000 characters, a cell holds at most 50,000. An image over 200,000 decoded bytes, not a JPEG, unreadable, or over the caps (6 a player and 120 in all per 6 hours) is refused cleanly: the report is logged all the same and the reply's `img` says `{id: 0}` (`{id: 1}` kept). The Reports tab gets a last column, `Image`, holding the report's id when a picture is attached (the header is written at the first one for a tab made before; the readers of the Id column now look it up by name, not as the last column). No new scope. An image never outlives its report (rule D7): the account's reports deleted, the images go (`repImgSweep_`); reports kept anonymised with "delete, keep answers", their images go and the mark with them; a merge or archive renames the Player column. The app turns the input on from this version (`REPIMG_SHEET`); an older script answers a report as before.
