Groups carry an instance's rights (`docs/decisions/2026-11-19-groups-carry-rights.md`; the groups-carry-rights study's PR 1). A group's rights are a new Rights column of the Group settings tab (`right@scope` entries: `players`, `settings`, `grant`, `content`, `live`, `cohorts`, each at `instance:imr`), and a membership of a group that carries rights holds the account's code hash in a new Code hash column of the Groups tab; `can_` answers the union of the admin list's rights and the rights of the groups the account is in under its code hash. The admin list is the Roles tab's `admin` rows, kept apart from the groups: `roleGrant` / `roleRevoke` take `admin` at `platform` only. Only the grant right changes a group's rights or the members of a group that carries rights (`users_`, checked again under the lock in `usersDo_` and `groupDo_`), one name a call, never a list, a first right refused while the group has members (`members`); each change is audited (`join` / `leave <group id>`, `right+` / `right-`, one `grant` / `revoke … (via <group id>)` row per member), and a membership is never without its `ok` row (`joinPut_`, `joinAudited_`). A merge moves the merged-away account's groups without rights and drops its groups with rights and its place on the admin list, each audited (`mergePlan_`: the reply's `join`, `drop`, `admin`, and a new read `{mergePlan: {from, into}, token}` for the warning before it); a delete and an archive drop them the same way (`rightsDrop_`, rule D7). The player list gives each group's `rights` and each player's `roff` (groups with rights whose membership's code hash is not the account's). A one-shot migration (`ONCE_` rights, `rightsMigrate_`, read before it by `rightsBefore_`) makes the Roles tab's instance roles groups, nothing lost: owner "Managers", editor "Curators", trainer "Trainers" (ids `r:<role>`), each grant a membership under its code hash and Since, one `join … (migration)` Audit row each; the Roles tab keeps every row.
