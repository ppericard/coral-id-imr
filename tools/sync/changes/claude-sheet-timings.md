A small `Timings` tab measures how the sheet copes as the answer log grows (the storage study of 2026-11-14, step 1: "log ms and rows for each full read and for each save, sampled, in a small tab with no player data"; Pierre, 2026-11-14, Q352: the answer log moves to Cloudflare D1 only when a measured threshold is crossed): one row per measured operation (Time, Op, Ms, Rows, Cols, Version, Weight), never a name, code, device, answer id or answer content (rules D2, D7). Measured: the whole-tab reads of `Answers` (`logRows_`) and of its Id column (`freshAnswers_`, `logAnswers_`), the photo stats' build (`stats_`), every player's saved data (`datas_`), the leaderboard's replays (`boardWarm_`), and as a whole a completed save, an anonymous send that logged, a load, a public stats request, the admin's readAnswers and each run of the 15-minute trigger. Sampled per request (`TIM.EVERY` 50; trigger runs `TIM.EVERY_TRIGGER` 16) at that weight, plus every operation slower than `TIM.SLOW` 5 s (a trigger run 60 s) at weight 1; kept in memory and written at the end of the request (`timEnd_`, from `doGet` / `doPost` / `autoUpdate`'s finally, after every lock is released), one `appendRow` a row inside try/catch, so a failure never touches a reply. The trigger keeps the tab bounded (`timTrim_`): past `TIM.MAX` 4,000 rows the oldest half is thinned to one row in two within each operation (`timThin_`), each kept row carrying the weight of the one it replaces; past twice that nothing more is written. Read with `tools/timings.js`. Nothing a player sees changes.
